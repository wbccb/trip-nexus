# LLM延迟优化
1. 先从 4 次 → 2 次
   - 第 1 次：合并“实体抽取 + 意图识别”（可保留可选的摘要更新标记）
   - 第 2 次：行程生成/修改（半小时粒度 + 坐标/城市/街道）
2. 会话摘要改成按需 + 异步
   - 当消息数超过阈值时，后台调一次大模型生成/更新摘要
   - 不再把摘要生成塞在用户同步请求链路里
3. 后续再视情况引入本地小模型
   - 当你接入了 Ollama/本地模型之后，可以把第 1 次调用迁到本地小模型，只保留行程生成用云端/大模型

## 1.收敛成「2 次大模型调用」
1. 第一次调用：实体抽取 + 意图识别（合并）
- 将原来的 实体抽取 (1) + 意图识别 (3) 合并到一次调用中：
  - 输入：
    - 最近 N 条对话（含用户最新消息）
    - 当前行程简要（如果有）
  - 输出 JSON：
    - entities ：目的地、日期、预算、人数、偏好
    - intent ：none/plan_new/modify_trip/add_attraction/delete_attraction/reorder_trip
    - edit_target ：涉及的天数/景点 id/时段等
  - 优点：
    - 这两个任务高度相关，同一份上下文即可完成
    - 逻辑简单：你只需要一个工具 analyze_user_message 
2. 第二次调用：行程生成/修改（整合一切约束）
- 将原来的 行程生成/修改 (4) 保持单独一步：
  - 在调用前，你已经有：
    - entities （第 1 次输出）
    - intent
    - 现有行程结构（如果存在）
    - 由天气/地图/RAG 工具得到的“硬约束/软约束”（可按需调用 MCP）
    - 已有的长期摘要（不需要每次重新生成）
  - 这一步的大模型只负责：
    - 按半小时粒度输出新的 Itinerary JSON
    - 保证坐标/城市/街道信息存在（你在 v0.0.3 里要求的）

## 2.收敛成【2次大模型调用】 => 【小模型 + 规则】 + 【1次大模型调用】

1. 小模型：实体抽取、意图识别、会话摘要
2. 大模型：行程生成/修改


## 尝试优化1
### 耗时过长的根因（按同步链路）
- 主要时间都消耗在 LLM 推理上：一次会话里你日志里已经看到 analyze_user_message ≈ 23s + generate_trip ≈ 76s ，这两段基本就是“卡住点”。
- 额外的隐形耗时来自「重复的实体抽取」：原流程在 UI 里会先 process_new_message() 做一次实体抽取（会触发 LLM），再调用 analyze_user_message() （又一次 LLM），最后生成/修改行程（第三次 LLM）。而且之前实体抽取用的是 get_llm() 默认返回的 generation 模型（更慢）( llm_manager.py:L122-L129 )。
### 修复与增强（用于定位 + 降低无谓延迟）
- 消除“重复实体抽取”的同步 LLM 调用：把 analyze_user_message() 的 intent_data.parameters 直接合并进 CoreEntity ，从而在 UI 主链路上不再额外调用一次 LLM 做实体抽取 ( conversation_manager.py:L34-L56 )，并在 UI 中把调用顺序调整为“先分析，再入库/合并实体” ( ui_manager.py:L340-L368 )。
