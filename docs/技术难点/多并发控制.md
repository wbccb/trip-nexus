# 多并发控制请求

多源搜索（SearXNG）、网页抓取、LLM 调用都是 I/O 密集型任务，但每一层的负载形态、超时风险和可用性诉求不同，需要分层选择并发模型并配套限流、超时、熔断与降级。

## 1. 主流并发方式对比（Python）

| 方式 | 适用场景 | 优点 | 主要风险 |
| --- | --- | --- | --- |
| threading + ThreadPoolExecutor | 同步 HTTP 客户端、阻塞式 SDK | 与现有同步库兼容、迁移成本低 | 线程过多导致上下文切换开销、连接池耗尽 |
| multiprocessing / ProcessPoolExecutor | CPU 密集任务（向量计算、NLP 重排序） | 避开 GIL，吞吐稳定 | 进程间通信成本高、内存占用大 |
| asyncio + aiohttp/httpx | 大量短连接 I/O 并发 | 单线程高并发、可控超时/取消 | 任意同步调用会阻塞事件循环 |
| anyio / asyncio.TaskGroup | 统一 async 生态和取消语义 | 结构化并发、异常传播更清晰 | 需要统一 async 调用链 |
| gevent / eventlet | 需要最小改动的协程化 | 兼容性高，改造成本中等 | monkey patch 风险，第三方库不稳定 |
| 任务队列（Celery/RQ） | 长耗时、可异步离线执行 | 解耦、失败可重试 | 延迟提升，不适合实时响应 |

## 2. 结合 v0.0.2 的并发场景拆解

### 2.1 多源搜索（SearXNG + fallback）
- 现状：串行尝试多个实例，超时会拖慢整体响应。
- 并发策略：并行探测多个实例，首个成功即返回，其余请求主动取消。
- 风险控制：为每个实例设置连接/读取超时，失败实例进入短期熔断窗口。

### 2.2 网页抓取（Top K 页面）
- 现状：ThreadPoolExecutor 并发抓取，单个请求超时 10s。
- 并发策略：保留线程池，但增加每域名并发上限和全局并发上限。
- 风险控制：限制每次抓取字节数与 HTML 解析时间，避免长页卡死。

### 2.3 LLM 多阶段调用（意图识别/摘要/行程生成）
- 现状：同步串行调用，整体延迟由单次最慢模型决定。
- 并发策略：保持主链路串行，异步并行执行可选的预取信息（天气/POI）。
- 风险控制：对外部模型配置并发上限与速率限制，避免触发限流。

## 3. 推荐并发方案（面向 TripNexus）

### 3.1 搜索层：并行探测 + 快速熔断
- 并行发起 3~4 个 SearXNG 实例请求，设置 2~3 秒连接超时 + 5~7 秒读取超时。
- 首个成功结果直接返回；其余请求取消并释放连接。
- 失败实例进入熔断窗口（例如 60~120s），窗口内不再请求。
- 所有实例失败则降级到 DuckDuckGo HTML 或缓存结果。

### 3.2 抓取层：受控并发 + 负载保护
- ThreadPoolExecutor 或 asyncio + aiohttp 均可，但必须加信号量限制并发。
- 单次抓取设置最大正文长度与最大解析耗时，避免极端页面拖垮线程。
- 按域名并发限制（例如每域名 2 个并发），防止被封或触发 429。

### 3.3 LLM 层：限流 + 重试 + 预算
- 每个模型供应商独立并发上限（例如 OpenAI 2~4 并发）。
- 采用指数退避重试，但控制重试预算（避免雪崩重试）。
- 对可选步骤（例如扩展检索）设置总体 deadline，超时直接跳过。

### 3.4 结构化并发与全链路超时
- 设置“全局请求预算”（例如 12~18 秒），超出则进入降级逻辑。
- 统一使用结构化并发（TaskGroup/AnyIO），确保取消传播和资源释放。
- 不允许阻塞调用出现在 async 事件循环线程中。

## 4. “超时的快速熔断”设计要点

- 超时分层：连接超时、读取超时、总超时三层同时配置。
- 熔断条件：连续失败 N 次或超时比例超过阈值即熔断。
- 半开探测：熔断期结束后只允许少量探测请求。
- 退避策略：每次失败增加冷却时间，防止瞬时雪崩。
- 首次成功即恢复：一旦探测成功立即恢复正常并发。

## 5. Python asyncio vs Node Event Loop 的坑点

### 5.1 最大坑点
- Python 的 asyncio 对阻塞调用极度敏感，任意同步 HTTP/DB 调用会阻塞整个事件循环。
- GIL 使 CPU 密集任务即使放在协程中也无法并行，需要进程池。
- 取消语义更复杂，未正确处理会导致“幽灵任务”与连接泄漏。

### 5.2 避免方式
- 全链路 async：统一使用 aiohttp/httpx 等异步库。
- CPU 任务进程化：把向量重排、embedding 计算放到进程池。
- 使用 TaskGroup/AnyIO 管理子任务，确保异常与取消传播。
- 明确设置超时与并发上限，避免无限创建任务。
- 使用 uvloop 提升事件循环性能，减少调度开销。

## 6. 本项目的落地优先级

1. 搜索层引入并行探测与熔断机制，避免单实例挂起拖慢全链路。
2. 抓取层引入域名并发限制与最大正文长度限制，提升稳定性。
3. LLM 层引入并发上限与 deadline，避免尾部延迟拖垮用户体验。
4. 如果后续迁移到 asyncio，全链路异步优先，避免局部异步+大量同步调用的混搭。
