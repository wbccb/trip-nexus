# 多轮对话:上下文管理与压缩

## 豆包如何管理上下文
1. 短期窗口缓存：存储最近N轮对话，优先保障 “最近几轮” 对话的语义连贯 => Redis
2. 核心实体存储：每次新的用户会话进行提取`不变 / 关键信息`并缓存对话关键信息（如行程目的地、预算） => 内存 + 数据库
3. 长期摘要缓存：压缩早期对话内容为`摘要`（减少token消耗） => 数据库(MySQL)

## 豆包对话核心技术

#### 步骤1: 会话初始化与唯一标识，基于`用户ID` + `设备ID` + `时间戳`生成`session_id`

#### 步骤2: 增量式上下文信息提取，每次对话结束后不存储对话文本，而是增量提取`新的关键信息`，更新核心实体存储和长期摘要，避免冗余

技术实现：
1. 用 LLM 做 “增量信息提取”（Prompt 引导 + 结构化输出）
2. 基于 Pydantic 定义实体模型，强制结构化，避免解析混乱
3. 实体去重与更新（如用户多次修改预算，只保留最新值）


#### 步骤3: 分层存储更新（短期+核心实体+长期）

每次有新的对话到来的时候
- 如果对话已经超过10轮，则对最早的对话进行压缩（长期）
- 将新的对话中的实体进行提取，然后更新对应的实体数据对象（核心实体）
- 存储最新的对话内容 => 全部存储（短期）

#### 步骤4: 构建LLM输入前，进行动态优化（压缩+截断+排序）

1. 摘要融合：将`长期摘要` + `核心实体`融合为一段结构化文本
2. 冗余过滤：如果最新对话的内容是`重复信息`和`无关信息`（比如你好，谢谢）则进行对应的不处理，只存储在短期会话窗口中 => 寒暄信息不存入核心实体和长期摘要，仅保留在短期窗口（10 轮后自动删除）
3. 动态截断：计算token（用`tiktoken`或者`HuggingFace tokenizers`进行计算），如果超过4096token，按照优先级：`核心实体` > `最近3轮对话` > `长期摘要` > `超过3轮的早期对话内容`进行数据的保留

#### 步骤6: 会话持久性和恢复

> 为了支持 “刷新页面 / 切换设备” 后上下文不丢失，豆包会将会话数据持久化到存储介质，同时支持快速恢复

- 2小时内的活跃会话：Redis
- 超过2小时的历史会话：MySQL/PostgreSQL
