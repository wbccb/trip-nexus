# 流式输出 & POI绘制

## 1. 结合 v0.0.2 的应用场景

- 前端多轮对话输出较长，单次回复包含结构化行程+说明文本，流式输出可明显降低首字延迟。
- RAG 链路中，搜索与抓取需要时间，流式输出可先返回骨架/概要，再补全细节。
- 地图与行程联动要求“按天/按序”逐步渲染 POI，避免一次性大量渲染导致卡顿。

## 2. 流式输出的主流实现方式

- SSE（Server-Sent Events）：服务端持续推送文本块，浏览器 EventSource 接收。
- Fetch Stream：fetch + ReadableStream 自行解析 chunk，控制更灵活。
- WebSocket：双向通信，适合需要客户端反馈与多路复用的场景。

## 3. Ollama 流式输出的落地方式

- 服务端向 Ollama 开启 stream 模式，按 token chunk 输出。
- 对外提供 SSE 或 Fetch Stream 代理接口，统一规范为前端可消费的增量消息格式。
- 每个 chunk 包含字段：content_delta、sequence、message_id、is_final，用于保证顺序与结束态。

## 4. Markdown 实时渲染抖动优化

- 双缓冲渲染：流式接收先写入隐藏缓冲区，按固定节奏（如 80~120ms）批量 flush。
- 增量 diff：只对新增段落渲染，避免全量 Markdown 重排。
- 分段冻结：对已结束的段落锁定 DOM，不再参与重排。
- 预估骨架：先渲染标题与段落占位，后续替换内容，减少布局抖动。
- 降级策略：超长输出时切换为纯文本流式，最终再一次性 Markdown 渲染。

## 5. POI 按序准实时绘制方案

### 5.1 数据通道设计

- LLM 输出约束为结构化分段：Day -> TimeBlock -> POI。
- 解析器在收到完整 POI 节点后立即发出 “poi_ready” 事件。
- 事件队列按 sequence 排序，保证绘制顺序一致。

### 5.2 渐进式渲染策略

- 分批渲染：每批 3~5 个 POI，批间隔 200~400ms，保持平滑。
- 层级渲染：先渲染当前天 POI，完成后再渲染下一天。
- 地图空闲时渲染：利用 requestIdleCallback 或 rAF 控制绘制节奏。

### 5.3 失败与降级

- POI 坐标缺失：先绘制文本行程，地图端用占位符标记。
- POI 过多：切换为聚合渲染或按视口加载。
- 流式中断：保留已绘制状态，等待补全时从最后序号继续。

## 6. 推荐实现路径（最小改动）

1. 继续使用 SSE 或 Fetch Stream，定义统一 chunk 协议。
2. 前端引入节流渲染与增量 Markdown 更新，减少重排。
3. POI 输出格式收敛为可流式解析的分段 JSON。
4. 地图渲染增加批处理与按天渲染策略，保证平滑。
