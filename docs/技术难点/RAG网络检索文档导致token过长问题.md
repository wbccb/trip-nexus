# RAG网络检索文档导致token过长问题

> 在前端交互上，如果 RAG 检索出的参考文档非常多，导致 Context 窗口溢出，前端是如何引导用户进行“检索结果人工介入”的？或者是完全依赖后端自动裁剪？

## 1. 结合 v0.0.2 的触发点

- 多源搜索结果聚合后，摘要数量可能远超可用上下文。
- 内容抓取返回正文很长，直接拼接会撑爆上下文窗口。
- 行程生成既要结构化输出又要带来源解释，导致 token 占用叠加。

## 2. 主流解决路径

### 2.1 后端自动裁剪优先

- 多阶段过滤：搜索摘要粗筛 -> 语义重排 -> Top K 正文抓取。
- 文档级压缩：对每个文档做摘要，限制单文档 token 预算。
- 片段级截断：按段落切块，只保留与 query 相似度最高的段落。
- 动态预算：在全局 token 预算内，按重要性分配给不同来源。

### 2.2 前端人工介入补强

- 显示检索来源列表，让用户勾选保留的来源或段落。
- 提供“缩小范围”快捷入口，例如限定城市/时间/玩法类型。
- 提示“当前证据过多”，引导用户选择 3~5 个权威来源。

## 3. 推荐的混合方案

- 默认后端自动裁剪，保证主链路无需用户干预。
- 当检索结果数量过多或内容过长时，前端弹出“精炼选择”面板。
- 保留低成本的“只看权威来源 / 只看最近 3 个月”快速筛选。

## 4. 具体落地策略（适配 TripNexus）

### 4.1 Token 预算分层

- 全局预算拆分为：系统提示 + 对话上下文 + RAG 证据。
- RAG 证据再拆为：摘要区 + 正文区，每区设置硬上限。

### 4.2 RAG 证据构建

- 摘要区：只保留 Top K 的搜索摘要，每条限制长度。
- 正文区：对抓取内容做分块向量检索，保留最相近的 N 段。
- 每段正文做长度限制，超出直接截断或再次摘要。

### 4.3 前端交互策略

- 检索结果面板显示来源、时间、权威标识，支持一键筛选。
- 显示“当前证据 token 预算使用率”，超标时提示缩减。
- 支持“仅保留已选来源 + 自动重排”按钮。

## 5. 可执行优先级

1. 后端加入片段级截断与摘要，确保默认不溢出。
2. 增加全局 token 预算管理，超出即自动裁剪。
3. 前端增加来源选择与快速筛选入口，作为兜底。
