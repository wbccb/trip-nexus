## frontend
1. 实现前端多轮对话交互
- **处理新消息机制**（区分角色处理以优化性能）：
  - **用户消息 (User Message)**：
    1. **冗余检测**：判断是否为寒暄/无效信息（如"你好"、"谢谢"）。
    2. **实体提取**：若非冗余，则基于现有上下文增量提取核心实体（目的地、预算、日期等）。
    3. **存入窗口**：追加到短期记忆窗口。
  - **助手消息 (Assistant Message)**：
    1. **直接存入**：跳过实体提取，直接追加到短期记忆窗口。
  - **上下文维护（公共流程）**：
    1. **窗口滑动与压缩**：检查短期窗口消息数量（>10条）。
    2. **摘要生成**：若超出阈值，将最早的对话压缩为长期摘要并存入数据库。
    3. **状态持久化**：更新Redis短期缓存和数据库持久化存储。

- 动态优化上下文：prompt如果过长则进行对话内容的缩减：核心实体 > 最近3轮 > 长期摘要 > 早期对话
- 数据保存：保存历史的对话信息，在下一次加载时自动恢复对话内容
> 存储完整的对话历史（用户 + 助手）
> 从用户消息中提取核心实体
> 对长期对话进行压缩和摘要（用户 + 助手）
> 为 LLM 提供优化后的上下文

- **行程修改机制**：
  - **增量更新**：支持"修改"（modify_trip）、"新增"（add_attraction）、"删除"（delete_attraction）、"重排序"（reorder_trip）四种意图。
  - **参数继承**：在修改行程时，新的参数（如天数、预算）会覆盖原有参数，未提及的参数则继承自原行程。
  - **智能Prompt**：构建Prompt时，会自动将修改意图（edit_note）和最新的上下文一并传给LLM，确保生成的行程符合用户的最新要求。

2. 交互流程完善：
- 多轮对话后可以生成对应的旅游行程 + 地图数据，然后左边是多轮对话输入框 + 右边是地图和文字行程显示
- 左边可以继续输入文字，根据之前生成的上下文重新完善行程，然后重新渲染右边地图和文字行程

3. 初始化会话
- **Session ID 生成**：基于 `用户ID` + `设备ID` + `时间戳` 生成唯一标识
- **多级上下文恢复**：
  1. **短期缓存 (Redis)**：优先检查是否存在活跃会话（2小时内），如果存在直接恢复上下文。
  2. **持久化存储 (DB)**：如果短期缓存未命中（过期或首次加载），尝试从数据库检索历史聊天记录。
     - 若存在历史记录，自动重建会话上下文，加载最近10条消息到短期窗口，并恢复长期摘要和核心实体。
     - 若无历史记录，则初始化为全新会话。
- **目的**：确保用户刷新页面或长时间离开后，对话状态（如行程偏好、历史上下文）不会丢失。


总结4次LLM调用
- 抽取实体
- 当消息超过10条时，对第一条消息进行总结压缩，行成摘要
- 意图识别出用户想要的行程修改意图（modify_trip）、新增意图（add_attraction）、删除意图（delete_attraction）、重排序意图（reorder_trip）
- 整合实体、摘要、意图进行LLM的构建，然后进行新的行程的生成

## rag

- **核心流程编排** `src/rag/rag_main.py`: 实现完整的 Search -> Filter -> Crawl -> Store -> Retrieve -> Answer 闭环。
- **意图识别** `src/rag/module/intent_recognition.py`: 使用 Sentence-BERT 初步分类 + LLM 复杂意图识别的双阶段策略。
- **多源搜索** `src/rag/network/multi_source_search.py`: 基于 SearXNG 聚合搜索，根据意图动态选择搜索引擎策略。
- **质量过滤** `src/rag/module/quality_filter.py`: 引入 CrossEncoder (MiniLM) 对搜索摘要进行语义重排序，优选高质量结果。
- **内容抓取** `src/rag/network/crawler.py`: 并发抓取 Top K 网页正文，包含自动编码检测和噪声清洗。
- **向量存储** `src/rag/store/vector_store.py`: 集成 ChromaDB 和 HuggingFace Embeddings，建立临时向量索引支持 RAG 检索。
