# v0.0.6

## 一、版本定位

v0.0.6 的核心目标：在延续 v0.0.5「单主流程」稳定性的前提下，完成从“行程生成工具”到“中立旅行决策与共创平台”的产品能力升级。

本版本不与 OTA 在交易履约上正面竞争，聚焦三类差异化价值：
1. 深度信息整合：融合公网长尾内容与用户私有知识。
2. 人机协同创作：支持可编辑、可回滚、可解释的行程共创过程。
3. 非标场景规划：优先解决复杂约束场景而非标准化热门线路。

## 二、版本目标（对应护城河方向，含社交接入 L0-L3 全链路落地）

1. **知识护城河目标**：将“知识库”从技术能力升级为 C 端高感知功能，形成用户私有旅行资产沉淀。
2. **体验护城河目标**：将 HITL + Agent Checkpoint 能力前台化，建立“可控修改、局部重排、结果可解释”的交互闭环。
3. **场景护城河目标**：补齐非标规划所需的“约束输入 + 冲突检测 + 替代方案”能力。
4. **生态护城河目标**：建立行程导出与分发能力，把 TripNexus 定位为决策上游入口。

## 三、范围定义

### 3.1 本版本纳入范围

1. 旅行灵感收纳箱（Knowledge Base 产品化）
   - 支持更明确的知识来源管理与使用状态感知。
   - 支持在生成行程前设置“本次优先参考的知识资产”。
   - 社交 URL 分层接入能力在 v0.0.6 落地 L0-L3 全链路（含 L2 有限平台适配、L3 浏览器渲染兜底）。
2. 行程约束显式化（Constraints UI + Prompt 注入）
   - 增加预算、体能强度、节奏偏好、家庭友好等约束参数。
   - 约束参数进入主流程并参与生成/修改。
3. 冲突检测与解释（Conflict Check）
   - 针对时间冲突、路程过长、节奏过密给出 warning。
   - 提供 Plan A / Plan B 两套替代建议。
4. 局部重排增强（Replan by Scope）
   - 支持“锁定不改动天数 + 指定单天/半天重排”。
   - 保留原有 Agent 升级与恢复能力。
5. 分享与克隆（Fork & Tweak）
   - 支持结构化行程生成分享链接。
   - 支持基于分享行程继续微调。

### 3.2 本版本不纳入范围

1. 不建设机票/酒店交易闭环，不接入支付与订单系统。
2. 不做全量社交社区，仅落地“分享与克隆”的最小闭环。
3. 不新增重型推荐系统，仅在现有 LLM + RAG + 工具体系上扩展规则与流程。

## 四、需求规划（按能力域）

### 4.1 旅行灵感收纳箱（P0）

#### 4.1.1 用户价值
1. 用户可把碎片化攻略、游记、PDF 变成可复用的个人知识资产。
2. 行程生成时可被“定向引用”，避免 AI 输出泛化模板行程。

#### 4.1.2 功能需求
1. 知识库管理增强
   - 显示知识库来源类型（PDF/Markdown/URL/TXT）。
   - 显示知识条目数量与最后更新时间。
2. 生成链路接入增强
   - `knowledge_base_id` 保持必传可选。
   - 新增 `knowledge_query` 默认值策略（当用户未填写时，自动基于目标地 + 偏好构建查询）。
3. 证据可见性
   - 前端可查看本次使用的 summary/body evidence 摘要。
   - 支持“仅使用私有知识 / 私有+公网融合”开关。

#### 4.1.3 社交数据接入策略

> 详细技术方案见 `docs/技术难点/社交URL内容获取方案.md`

1. 核心策略
   - 按”内容获取方式分层”而非”按平台逐一攻克抓取”。
   - 对开放网页：自动抓取做到稳定。对高风险社交平台：用户辅助导入做到顺滑。
   - 不做反爬对抗能力，不绕过平台访问限制。

2. 平台分级（v0.0.6 落地）
   - **低风险**（博客、媒体、攻略站）：`requests + bs4` 自动提取，高成功率。
   - **中风险**（知乎公开问答、B站）：自动提取 + 质量门禁，失败时引导手动导入。
   - **高风险**（小红书、微博）：用户辅助导入优先，自动抓取仅 best effort。
   - 平台识别范围：`xiaohongshu`、`weibo`、`zhihu`、`bilibili`、`unknown`。

3. 分层获取架构（v0.0.6 落地 L0 + L1 + L2 + L3）
   - **L0 URL 预处理层**：URL 规范化、去追踪参数、短链解跳（`xhslink.com`/`b23.tv`/`t.cn`）、平台识别、风险等级识别。
   - **L1 开放网页自动提取层**：复用现有 `requests + BeautifulSoup`，补齐元信息提取（`og:title`/`og:description`）和质量门禁。
   - **L2 有限平台适配层**（v0.0.6 落地）：仅做最小化元信息 + 公开首屏正文提取，不承诺评论区/多页/登录后内容。
   - **L3 浏览器渲染兜底层**（v0.0.6 落地）：Playwright 仅用于公开页 CSR 补救，不负责绕过登录/风控。

4. 入库前质量门禁（v0.0.6 落地）
   - 新增 `validate_content_quality(content_text, metadata)` 函数。
   - 检查项：最小字符数（`>= 80`）、有效文本密度（`>= 0.15`）、中文内容比例（`>= 0.3`）、重复段比例（`< 0.4`）、噪声模板命中。
   - `quality_score` 0-100，入库阈值 `>= 40`。
   - 去重判定：同 `knowledge_base_id` 下相同 `resolved_url` 已有高相似度条目则拒绝入库。

5. 新增错误码（v0.0.6 落地）
   - `AUTO_PARSE_EMPTY`：有效文本 < 80 字符
   - `AUTO_PARSE_LOW_QUALITY`：quality_score < 40
   - `AUTO_PARSE_DUPLICATED`：重复内容
   - `AUTO_PARSE_BLOCKED`：命中”下载 App”等关键词
   - `AUTO_PARSE_LOGIN_REQUIRED`：命中登录提示关键词
   - `AUTO_PARSE_RISK_VERIFICATION`：命中验证码/人机验证关键词
   - `AUTO_PARSE_PAYWALLED`：命中会员/付费关键词
   - `URL_RESOLVE_LOOP`/`URL_RESOLVE_TIMEOUT`：短链解跳异常

6. 前端交互增强（v0.0.6 落地）
   - URL 输入后、导入前：根据 `source_risk_level` 展示前置引导文案（低风险默认自动、高风险默认手动）。
   - 导入失败后：按 `source_platform` + `ingest_error_code` 展示平台级引导文案，引导用户切换手动导入。
   - 来源列表增加：平台标签（带图标）、风险等级颜色标识、错误码 hover 说明。

7. P1 范围（下版本）
   - 登录态授权导入（仅在用户授权和平台规则允许时启用）。
   - 图文 OCR、短视频字幕抽取等多模态增强。

8. P2 范围（后续）
   - 浏览器插件/书签脚本授权导入。
   - 按 ROI 建设平台专属 connector。

9. 合规边界
   - 不绕过平台访问限制，不破解登录态，不提供反爬对抗策略。
   - 支持数据可追溯、可删除、可过期。


### 4.2 行程约束显式化（P0）

#### 4.2.1 用户价值
1. 用户可直接表达“预算/体力/家庭成员限制”等硬条件。
2. 降低反复口头修正成本，提升首版行程可用度。

#### 4.2.2 功能需求
1. 约束输入面板
   - 预算档位：经济/均衡/舒适。
   - 体能强度：休闲/标准/特种兵。
   - 节奏偏好：文化探索/打卡效率/亲子友好。
   - 特殊约束：步行上限、午休需求、无障碍需求。
2. 约束协议统一
   - 前端将约束归一为结构化对象。
   - 后端在主流程内注入 LLM prompt 与重排行为。
3. 结果可追踪
   - 输出中标记关键约束是否满足（如“已控制单日步行强度”）。
   - 前端展示约束满足状态，后端在主流程内注入 LLM prompt 与重排行为。

#### 4.2.3 对应现有模块
1. 前端：`web/src/components/TripTab.jsx`、`web/src/hooks/useTrip.js`
2. 后端：`src/llm/llm_manager.py`（build_prompt / change_trip）

### 4.3 冲突检测与解释（P0）

#### 4.3.1 用户价值
1. 在不合理行程出现时给出明确原因，而不是直接失败或静默改写。
2. 用户可在“坚持原方案”和“接受替代方案”之间做决策。

#### 4.3.2 功能需求
1. 冲突检测规则
   - 距离与时间冲突（半天跨城、连续超长交通）。
   - 节奏冲突（单日 POI 过密、无休息窗口）。
2. 解释与替代输出
   - 输出冲突原因文本。
   - 输出 Plan A（保守可执行）/Plan B（满足偏好但风险更高）。
3. 流式事件扩展
   - 在 `step` 事件中增加 `warning/conflict` 类型，前端高亮展示。

#### 4.3.3 对应现有模块
1. 后端：`src/api/app.py`（流式事件输出）、`src/llm/llm_manager.py`
2. 前端：`web/src/api/flowApi.js`、`web/src/components/TripTab.jsx`

### 4.4 局部重排与可控共创（P1）

#### 4.4.1 用户价值
1. 用户可只改动某一天或某半天，减少“全局重算导致满意部分被破坏”。
2. 强化用户掌控感，提升多轮编辑体验。

#### 4.4.2 功能需求
1. 锁定机制
   - 支持锁定 day/block，不参与重排。
2. 局部重排
   - 支持“仅重排第 N 天”或“第 N 天下午”。
3. Agent 升级条件联动
   - 当局部重排触发跨天依赖时，自动升级 Agent 并返回触发原因。

#### 4.4.3 对应现有模块
1. 后端：`src/agent/agent_loop.py`、`src/api/app.py`
2. 前端：`web/src/components/TripTab.jsx`、`web/src/components/TripMap.jsx`

### 4.5 分享与克隆（P1）

#### 4.5.1 用户价值
1. 用户可快速把结构化成果外发，形成自然传播。
2. 新用户可在现有方案上二次编辑，降低冷启动门槛。

#### 4.5.2 功能需求
1. 分享
   - 生成可访问链接（包含行程结构与必要摘要）。
2. 克隆
   - 新会话可加载分享方案并继续编辑。
3. 权限与安全
   - 默认匿名分享，不包含用户隐私上下文。

#### 4.5.3 对应现有模块
1. 前端：`web/src/App.jsx`、`web/src/hooks/useTrip.js`
2. 后端：`src/api/app.py`（新增分享/克隆接口）

## 五、非功能需求

1. 性能
   - 常规生成链路时延相对 v0.0.5 增量不超过 20%。
2. 稳定性
   - 冲突检测失败不阻断主流程，自动降级为普通生成并记录 warning。
3. 可观测性
   - 新增指标：`constraint_used`、`conflict_detected`、`plan_alternative_generated`、`share_created`、`fork_started`。
   - 新增社交导入指标：`social_ingest_total`、`social_ingest_success_rate`、`social_ingest_fallback_rate`、`social_ingest_by_platform`（按平台统计）、`social_ingest_by_risk_level`（按风险等级统计）、`quality_gate_reject_rate`（质量门禁拒绝率）。
4. 可维护性
   - 新增字段优先复用现有 `/api/flow/stream` 协议，不新增并列主链路。
5. 合规性
   - 社交链接接入全链路保留来源 metadata 与删除能力，满足最小合规要求。

## 六、验收标准

### 6.1 功能验收

1. 旅行灵感收纳箱可完成创建、上传、选择并参与行程生成。
2. 社交链接导入可完成”解析成功入库”与”解析失败降级导入”两条路径。
   - URL 预处理（短链解跳、平台识别、风险分级）正常工作。
   - 质量门禁可拦截低质量/噪声页面并返回准确错误码。
   - 前端可根据平台和风险等级展示差异化引导文案。
3. 约束参数可被稳定传递并影响行程结果。
4. 冲突场景可返回可解释 warning 与替代方案。
5. 局部重排支持锁定与指定范围改动。
6. 分享链接可打开并支持克隆后二次编辑。

### 6.2 体验验收

1. 用户在 3 次以内编辑中可完成“初版->可执行版”行程收敛。
2. 冲突提示可读且可操作，不出现“只报错不给建议”。
3. 局部重排后，未锁定部分保持最小变更原则。

### 6.3 技术验收

1. 主流程事件协议兼容现有前端消费逻辑。
2. 新增功能不破坏 v0.0.5 的 pause/resume/retry 闭环。
3. 核心接口具备最小回归测试样例（知识库注入、约束注入、冲突警告、局部重排）。

## 七、优先级与排期建议

### P0（本版本必须落地）
1. 旅行灵感收纳箱产品化（可见性 + 使用策略）。
2. 约束输入面板与后端注入链路。
3. 冲突检测与解释输出（含流式 warning 事件）。
4. 社交内容接入网关 P0（通用 URL 解析 + 失败降级 + 来源标注）。

### P1（本版本应做）
1. 局部重排锁定机制。
2. 分享与克隆最小闭环。
3. 社交数据授权导入与多模态增强（OCR/字幕抽取）。

### P2（可延后）
1. 多平台外部导出（Notion/日历）标准化。
2. 逆向比价与分销链接能力。

## 八、版本成功判定（Go / No-Go）

满足以下条件可判定 v0.0.6 达标：
1. P0 功能全部上线并通过自测。
2. 常规链路稳定性不低于 v0.0.5。
3. 至少一个非标场景（如亲子/自驾/高强度）形成可复用演示样例。
4. 用户可感知“我的知识 + 我的约束 + 我的可控修改”三项核心差异化体验。




## 九、开发实施记录

### 9.1 旅行灵感收纳箱（P0）

#### 9.1.1 任务规划（前端 / 后端 / API / 数据结构 / 验收用例）
1. 前端任务规划（P0）
   - 在 `KnowledgeTab.jsx` 提供社交链接导入入口（URL 输入框 + 导入按钮）。
   - 增加导入状态机：解析中、成功、失败、降级建议（手动粘贴/OCR）。
   - 在来源列表展示 `source_type/source_platform/source_url/ingest_status`，并增强可读性（平台标签、风险标识、错误码提示）。
   - 支持失败后一键切换到手动导入模式（文本粘贴 + OCR 文本）。
   - URL 输入后调用预处理接口，按 `source_risk_level` 展示前置引导文案。
   - 自动导入失败后按 `source_platform + ingest_error_code` 展示平台级引导文案。
   - P1 延伸：增加失败来源展示、失败后补全文本重试入口、命中来源与来源总览分区展示、OCR/字幕导入入口。
2. 后端任务规划（P0）
   - 在 `app.py` 落地社交导入编排：参数校验 -> L0 URL 预处理 -> URL 抓取 -> 正文抽取 -> 质量门禁 -> 标准化 -> 入库。
   - 新增 `src/rag/network/url_preprocessor.py`：URL 规范化、去追踪参数、短链解跳、平台识别、风险等级映射。
   - 新增 `src/rag/network/content_validator.py`：`validate_content_quality()` 与质量评分（0-100，阈值 >= 40）。
   - 平台识别补齐 `zhihu.com` / `zhuanlan.zhihu.com`。
   - 引入 L2 有限平台适配层与 L3 浏览器渲染兜底层。
   - 在入库 metadata 中补齐 `normalized_url/resolved_url/source_risk_level/extractor_layer/quality_score` 等字段。
   - 增加来源删除、来源追踪、过期清理标记等合规能力。
   - P1 延伸：失败来源持久化、失败来源原位重试、`source_evidence` 精确命中反查、OCR/字幕文本标准入库编排。
3. API 任务规划（P0）
   - `POST /api/knowledge/bases/{knowledge_base_id}/ingest/url`：支持 `auto/manual` 导入与 fallback 返回。
   - `POST /api/knowledge/preprocess/url`：前端在输入 URL 后预获取平台与风险等级。
   - `GET /api/knowledge/bases/{knowledge_base_id}/sources`：返回来源列表与导入状态统计。
   - `DELETE /api/knowledge/bases/{knowledge_base_id}/sources/{source_id}`：按来源删除分块用于撤回。
   - P1 延伸：`sources` 返回失败来源与更完整错误信息；新增或扩展来源重试接口；`knowledge/search` 与 `flow/stream` 仅返回本次实际命中来源。
4. 数据结构任务规划（P0）
   - metadata 标准字段包含 `source_id/source_type/source_platform/source_url/ingest_mode/ingest_status/ingest_error_code/ingested_at/expires_at`。
   - metadata 扩展字段包含 `normalized_url/resolved_url/source_risk_level/extractor_layer/quality_score`。
   - RAG 检索结果透传 `source_type/source_platform/source_url/ingest_status` 用于前端证据展示。
   - P1 延伸：补齐 `failure_reason/last_retry_at/retry_count/hit_chunk_ids/hit_count` 等字段。
5. 验收用例规划（P0）
   - 解析成功：公开 URL 导入成功，`ingest_status=parsed`，可被检索命中。
   - 解析失败降级：自动解析失败后，手动文本补全成功，`ingest_status=fallback`。
   - metadata 完整性：来源字段可查询且前端列表可见。
   - 删除与撤回：删除 `source_id` 后对应分块不再被召回。
   - 合规边界：受限链接返回明确错误码，不触发绕过策略。
   - 平台分级引导、质量门禁、短链解跳、去重判定、L2/L3 提取路径均有回归用例。

- `preprocess/url` 现在会做一次无副作用的“试解析”，但不会做去重判定、失败来源落库或真正入库；它的作用是预判，不是替代 `ingest/url`。

### 9.3 冲突检测与解释（P0）

#### 9.3.1 任务规划（前端 / 后端 / API / 数据结构 / 验收用例）

1. 数据结构
   - 新增 `ConflictType` 枚举（Pydantic / Python Enum），定义冲突类别：
     ```python
     class ConflictType(str, Enum):
         DISTANCE_TIME = "distance_time"    # 距离与时间冲突（半天跨城、连续超长交通）
         PACE_DENSITY = "pace_density"      # 节奏冲突（单日 POI 过密）
         REST_WINDOW = "rest_window"        # 休息窗口冲突（无休息/用餐间隔）
     ```
   - 新增 `ConflictItem` 模型，描述单条冲突：
     ```python
     class ConflictItem(BaseModel):
         type: ConflictType                     # 冲突类别
         day: int                               # 冲突所在天（1-indexed）
         description: str                       # 冲突原因文本（面向用户）
         severity: Literal["warning", "error"]  # warning=可接受风险, error=强烈不推荐
     ```
   - 新增 `AlternativePlan` 模型，描述替代方案：
     ```python
     class AlternativePlan(BaseModel):
         label: str           # "Plan A" 或 "Plan B"
         strategy: str        # 策略概述（如"保守可执行方案：拆分跨城为两天"）
         trip_data: dict      # 替代行程的完整结构（与正常 trip_data 格式一致）
     ```
   - 新增 `ConflictReport` 模型，汇总冲突检测结果：
     ```python
     class ConflictReport(BaseModel):
         has_conflicts: bool                          # 是否存在冲突
         conflicts: list[ConflictItem] = []           # 冲突列表
         alternatives: list[AlternativePlan] = []     # 替代方案（Plan A/B）
     ```
   - 与现有模型关系：
     - `ConflictReport` 在 finalize 阶段附加到事件 payload，与 `constraints_used` / `constraints_satisfied` 并列。
     - `AlternativePlan.trip_data` 复用现有行程 JSON 结构，不引入新格式。

2. 后端
   - **冲突检测逻辑**（`src/llm/llm_manager.py`）：
     - 新增 `_detect_conflicts(trip_data: dict, constraints: TripConstraints) -> ConflictReport` 方法。
     - 检测规则实现：
       1. **距离与时间冲突**：解析每日行程中连续 POI 的城市/区域信息，若同一天内跨城（城市名不同）则标记；检查交通耗时是否连续 > 2h。
       2. **节奏冲突**：统计每日 POI 数量，对比 `intensity` 约束阈值（leisure ≤ 3, standard ≤ 5, extreme 无上限）；若超出则标记。
       3. **休息窗口冲突**：检查 11:30-13:30 区间是否有空档（用餐/休息），若 `need_nap=True` 则检查 12:00-14:00 区间是否有明确休息安排。
     - 冲突检测失败（异常）时返回空 `ConflictReport(has_conflicts=False)`，记录 warning 日志，不阻断主流程（符合非功能需求）。
   - **替代方案生成**（`src/llm/llm_manager.py`）：
     - 新增 `_generate_alternatives(trip_data: dict, conflicts: list[ConflictItem], constraints: TripConstraints) -> list[AlternativePlan]` 方法。
     - 仅在 `has_conflicts=True` 时调用。
     - 通过追加 LLM 调用生成 Plan A（保守方案）和 Plan B（满足偏好但高风险方案），prompt 中注入冲突描述。
     - 替代方案生成失败时返回空列表，不阻断主流程。

           - `conflict_detected = false`
           - `plan_alternative_generated = false`
         - 不再调用 `_generate_alternatives()`。
      6. 后端 `src/api/app.py -> _run_flow_stream()`
         - 不发送 `step: "warning"` 事件。
         - 直接在 finalize payload 中返回：
           - `trip_data`
           - `constraints_used`
           - `constraints_satisfied`
           - `conflict_report = {has_conflicts:false,...}`
      7. 前端 `web/src/hooks/useTrip.js`
         - 不会收到 `warning`。
         - 在 `finalize` 阶段把空冲突报告写入 `conflictReport`。
      8. 前端 `web/src/components/TripTab.jsx`
         - 不展示冲突 Alert
         - 不展示替代方案卡片
         - 每天标题旁也不会出现冲突 Tag

    - **场景 E：冲突检测过程本身异常，自动降级为“无冲突”**
      1. 后端 `src/api/app.py -> _run_flow_stream()`
         - 正常完成生成阶段，拿到 `trip_data`。
      2. 后端 `src/api/app.py -> llm_manager.build_conflict_report(...)`
         - 进入冲突检测总入口。
      3. 后端 `src/llm/llm_manager.py -> _detect_conflicts()`
         - 在解析 `daily_plan`、时间窗口、城市信息或其他规则判断时发生异常。
      4. 后端 `src/llm/llm_manager.py -> _detect_conflicts()`
         - 进入内部 `except` 分支。
         - 打印降级日志：
           - `"[LlmManager] 冲突检测降级，原因=..."`
         - 返回：
           - `ConflictReport(has_conflicts=False, conflicts=[], alternatives=[])`
      5. 后端 `src/llm/llm_manager.py -> build_conflict_report()`
         - 将该结果视为“未检测到冲突”继续处理。
         - 不抛异常到主流程。
      6. 后端 `src/api/app.py -> _run_flow_stream()`
         - 主流程不中断。
         - 不发送 `warning`。
         - 继续发送 `finalize`。
      7. 前端结果表现
         - 用户仍能拿到完整行程结果。
         - 只是 `conflict_report` 为空，前端不展示冲突区。
      8. 设计目的
         - 冲突检测在当前版本属于“增强能力”，不是阻断式校验。
         - 因此即使检测失败，也优先保证“行程可生成、链路可完成”。

    - **场景 F：冲突检测成功，但替代方案生成失败**
      1. 后端 `src/llm/llm_manager.py -> build_conflict_report()`
         - 先调用 `_detect_conflicts()`，成功得到 `has_conflicts=True` 和冲突列表。
      2. 后端 `src/llm/llm_manager.py -> _generate_alternatives()`
         - 进入替代方案 LLM 调用。
      3. 后端 `src/llm/llm_manager.py -> _generate_alternatives()`
         - 若模型返回格式错误、JSON 解析失败、或结果缺少合法 `trip_data`：
           - 进入内部 `except`
           - 打印降级日志：
             - `"[LlmManager] 替代方案生成降级，原因=..."`
           - 返回空列表 `[]`
      4. 后端 `src/llm/llm_manager.py -> build_conflict_report()`
         - 继续返回：
           - `ConflictReport(has_conflicts=True, conflicts=[...], alternatives=[])`
         - 记录：
           - `conflict_detected = true`
           - `plan_alternative_generated = false`
      5. 后端 `src/api/app.py -> _run_flow_stream()`
         - 仍然会发送 `step: "warning"`，因为冲突本身已经成立。
         - finalize payload 中也会保留 `conflict_report.conflicts`，只是 `alternatives` 为空。
      6. 前端 `web/src/hooks/useTrip.js`
         - 能正常收到 `warning` 和 `finalize`。
      7. 前端 `web/src/components/TripTab.jsx`
         - 仍然展示顶部冲突 Alert。
         - 但不会渲染 Plan A / Plan B 卡片区域，因为 `alternatives.length === 0`。
      8. 用户视角结果
         - 能知道“当前方案存在冲突”
         - 但当前轮没有自动替代方案可选
         - 主流程依旧完成，不会因为替代方案失败而整体报错
- **未完成 / 后续可迭代**：
  - 当前替代方案采用后会关闭冲突区域，不保留“原方案 vs 已采用方案”的历史对比视图。
  - 当前冲突检测为规则优先方案，尚未接入真实地图距离/时长 API 做精确校验。

### 9.4 局部重排与可控共创（P1）

#### 9.4.1 任务规划（前端 / 后端 / API / 数据结构 / 验收用例）

1. 数据结构
   - 新增 `ReplanScope` 模型，描述重排范围：
     ```python
     class ReplanScope(BaseModel):
         day: int                                          # 目标天（1-indexed）
         time_range: Optional[Literal["morning", "afternoon", "evening"]] = None
                                                           # 半天范围，None=整天
     ```
   - 扩展 `TripReplanDayRequest`，新增锁定与范围字段：
     ```python
     class TripReplanDayRequest(BaseModel):
         user_id: str
         device_id: str
         session_id: str
         day: int                                          # 目标重排天（保留兼容）
         scope: Optional[ReplanScope] = None               # 精细重排范围（优先级高于 day）
         locked_days: list[int] = []                       # 锁定不参与重排的天（1-indexed）
         replan_instruction: Optional[str] = None          # 用户自由文本（如"下午改成室内"）
         constraints: Optional[dict] = None                # 约束透传
     ```
   - 新增 `AgentEscalationInfo` 模型，描述 Agent 升级触发信息：
     ```python
     class AgentEscalationInfo(BaseModel):
         escalated: bool = False                           # 是否触发 Agent 升级
         reasons: list[str] = []                           # 触发原因列表
         message: str = ""                                 # 面向用户的解释文本
     ```
   - 扩展 `TripReplanDayResponse`，新增元信息：
     ```python
     class TripReplanDayResponse(BaseModel):
         session_id: str
         trip_data: dict
         replanned_scope: dict                             # 实际重排的范围描述
         agent_escalation: Optional[AgentEscalationInfo] = None  # Agent 升级信息
         conflict_report: Optional[dict] = None            # 重排后冲突检测结果
     ```
   - 与现有模型关系：
     - `locked_days` 与现有 `day` 字段互补：`day` 指定重排目标，`locked_days` 指定保护区域。
     - `scope` 为 `day` 的精细化替代；当 `scope` 存在时优先使用 `scope.day` 和 `scope.time_range`。
     - `conflict_report` 复用 9.3 中已定义的 `ConflictReport` 结构。

2. 后端
   - **锁定机制**（`src/api/app.py` + `src/llm/llm_manager.py`）：
     - `replan_trip_day()` 接收 `locked_days` 参数，在构建 `edit_cmd` 时将锁定天信息注入 prompt。
     - 锁定天的行程内容在 prompt 中以"以下天数已锁定，不可修改"格式传入，LLM 仅对非锁定天生成新方案。
     - 后端在 merge 阶段做硬校验：对比重排前后 `locked_days` 对应天的内容，若 LLM 意外修改锁定天则回退该天数据为原始版本，并记录 warning。
   - **半天重排**（`src/llm/llm_manager.py`）：
     - `build_prompt()` / `change_trip()` 支持 `time_range` 参数，生成 prompt 时限定重排范围为"第 N 天上午/下午/晚间"。
     - merge 逻辑中按时间段拆分：保留目标天非重排时段的 POI，仅替换目标时段内容。
     - 时间段定义：morning=开始~12:00, afternoon=12:00~17:00, evening=17:00~结束。
   - **Agent 升级条件联动**（`src/api/app.py` + `src/agent/agent_loop.py`）：
     - 在 `replan_trip_day()` 中增加跨天依赖检测逻辑：
       - 若重排目标天的首个 POI 依赖前一天尾部交通衔接，或重排导致后一天首个 POI 时间不可达，触发 Agent 升级。
       - 触发条件写入 `AgentEscalationInfo`，返回给前端。
     - Agent 升级后使用现有 `PlannerAgent` → `AgentExecutor` 流程，但 scope 限定为受影响的相邻天（而非全局重排）。
     - Agent 升级失败时降级为仅重排目标天，记录 warning。
   - **最小变更原则**：
     - merge 逻辑中对非目标天做 diff 校验，确保未锁定、未被 Agent 升级波及的天保持不变。
     - 重排后自动重算 `conflict_report`（复用 9.3 逻辑）。

    - `agent_escalation`：返回相邻天联动检测结果与说明文本。
    - `conflict_report`：返回重排后重算得到的冲突检测结果，复用 9.3 的结构。
  - 已新增：
    - `ReplanScope`
    - `AgentEscalationInfo`

- **后端局部重排主逻辑已接入 `src/api/app.py -> replan_trip_day()`**
  - 当前实际实现不是直接把“第 N 天整天替换”写回，而是拆成以下步骤：
    1. 解析请求范围
       - 若 `scope` 存在，则优先使用 `scope.day` 和 `scope.time_range`。
       - 若 `scope` 不存在，则退化为旧版整天重排。
    2. 规范化锁定天
       - 通过 `_normalize_locked_days()` 清洗 `locked_days`。
       - 自动剔除非法值、去重，并排除当前目标天，避免“既要重排又锁定同一天”的矛盾输入。
    3. 构建重排上下文
       - 通过 `_build_replan_context()` 把当前完整行程、目标天原始安排、锁定天原始内容、自由文本要求组装为上下文块。
       - 这些上下文会和 `edit_cmd` 一起传入 `LlmManager.generate_trip()`。
    4. 调用 LLM 生成候选重排结果
       - `edit_cmd` 中已经明确带入：
         - `scope`
         - `locked_days`
         - `replan_instruction`
       - 让模型从 prompt 层先知道“只能改哪一段、哪些天绝对不能动”。
    5. 执行 merge 合并
       - 使用 `_normalize_daily_plan()` 把原行程和重排行程统一成按天结构。
       - 若本次是整天重排：直接替换目标天。
       - 若本次是半天重排：通过 `_merge_day_items_by_scope()` 只替换目标时间段，保留目标天其他时段原始内容。
    6. 执行相邻天联动检测
       - 使用 `_detect_replan_escalation()` 做启发式跨天依赖检测。
       - 当前检测维度包括：
         - 目标天末尾与下一天开头是否存在跨城衔接
         - 下一天是否存在过早出发窗口
         - 上一天末尾是否过晚结束
         - 上一天末尾与目标天开头是否存在跨城衔接
       - 若命中，则返回 `agent_escalation.escalated=true`，并给出 `reasons/message`。
    7. 执行相邻天最小联动 merge
       - 当前版本没有直接复用 LangGraph 的 PlannerAgent 做真正的子图执行。
       - 实际采用的是“启发式最小联动”策略：
         - 若影响下一天，只允许微调下一天 `morning`
         - 若影响上一天，只允许微调上一天 `evening`
       - 通过再次复用 `_merge_day_items_by_scope()`，把影响范围控制在最小必要集合内。
    8. 执行锁定天硬回退
       - merge 完成后，对 `locked_days` 对应的天再次回写原始行程。
       - 即使模型误改了锁定天，也会在最终结果中被强制恢复。
       - 若检测到模型确实动过锁定天，后端会记录 warning 日志。
    9. 重算约束与冲突
       - 重排完成后重新计算：
         - `constraints_satisfied`
         - `conflict_report`
       - 然后再写回存储，保证后续刷新页面时状态一致。

- **后端辅助函数已补齐到 `src/api/app.py`**

- **当前实现与规划的差异说明**
  - 文档规划里写到“Agent 升级后使用现有 `PlannerAgent -> AgentExecutor` 流程”。
  - 当前代码还没有把 9.4 的局部重排正式接进 LangGraph 子图执行。
  - 目前实际落地的是：
    - `src/api/app.py` 内的启发式相邻天依赖检测
    - 受影响相邻天的最小范围 merge
  - 这样做的好处是：
    - 改动面更小
    - 可以先快速验证“局部重排 + 锁定保护 + 联动提示”的交互价值
  - 当前边界是：
    - 联动范围仍然局限于前后相邻天
    - 联动是否生效依赖 LLM 返回结果中是否包含相邻天内容
    - 尚未具备真正的“局部子图计划与执行”

#### 9.4.4 自测流程

1. 启动与准备
   - 启动后端与前端，先以标准约束生成一份 3 天行程，确认行程正常展示。

2. 单天整天重排回归（现有能力）
   - 点击第 2 天"重规划当日"（整天模式）。
   - 通过标准：第 2 天内容更新，第 1、3 天不变，约束仍生效。

3. 锁定天验证
   - 前端锁定第 1 天（点击锁图标，视觉变灰），再重排第 2 天。
   - 通过标准：
     - 请求 payload 中 `locked_days: [1]`。
     - 响应中第 1 天内容与锁定前完全一致。
     - 前端锁图标状态正确。

4. 半天重排验证
   - 点击第 2 天"重排下午"。
   - 通过标准：
     - 第 2 天上午景点不变。
     - 下午景点被替换，时间衔接合理。
     - `replanned_scope.time_range` 为 "afternoon"。

5. 自由文本指令验证
   - 重排第 2 天，输入"换成美食探店路线"。
   - 通过标准：重排后第 2 天以餐厅/美食街为主，prompt 中包含"美食探店"。

6. Agent 升级验证
   - 构造场景：第 2 天末尾为远郊景点，第 3 天首个为市区景点。重排第 2 天。
   - 通过标准：
     - `agent_escalation.escalated` 为 true。
     - 第 3 天首个景点出发时间被微调。
     - 前端展示升级提示。
   - 降级场景：模拟 Agent 超时，验证仅重排目标天，后端日志有 warning。

7. 重排后冲突检测联动验证
   - 重排后检查 `conflict_report`。
   - 通过标准：若产生新冲突，前端冲突区域更新；若无冲突，`has_conflicts` 为 false。

8. 向后兼容验证
   - 通过 curl 调用旧格式请求（仅 day 字段）。
   - 通过标准：退化为整天重排，无报错。

9. 当前已知边界
   - 半天重排的时间段切分（morning/afternoon/evening）为固定边界，不支持用户自定义时间区间（如 10:00-15:00）。
   - Agent 升级的跨天依赖检测依赖行程结构中的时间与地点文本解析，若 LLM 未在行程中明确标注交通衔接信息，可能漏检。
   - 锁定天的硬回退机制依赖逐天 diff 对比，对行程结构格式有一定假设（按天分组的 JSON 数组）；若 LLM 返回格式不一致可能需要额外解析兜底。
   - 当前版本不支持跨天拖拽重排（如将第 2 天的景点拖到第 3 天），仅支持按天/半天粒度的 LLM 重排。
