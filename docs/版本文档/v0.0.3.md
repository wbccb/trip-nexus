# v0.0.3

目标：集成FunctionCall/MCP + 初步的Agent逻辑，优化产品交互细节

开发步骤（llm + Agent）
1. 明确行程数据结构：补充半小时粒度的时间片设计，保证每个行程节点包含「城市名 + 街道 + 精确坐标」字段
2. 定义核心 FunctionCall 工具：实体抽取、会话摘要、意图识别（modify/add/delete/reorder）、行程生成/修改（支持半小时粒度）
   - 先从 4 次 → 2 次
      - 第 1 次：合并“实体抽取 + 意图识别”（可保留可选的摘要更新标记）
      - 第 2 次：行程生成/修改（半小时粒度 + 坐标/城市/街道）
   - 会话摘要改成按需 + 异步
      - 当消息数超过阈值时，后台调一次大模型生成/更新摘要
      - 不再把摘要生成塞在用户同步请求链路里
   - 后续再视情况引入本地小模型
      - 当你接入了 Ollama/本地模型之后，可以把第 1 次调用迁到本地小模型，只保留行程生成用云端/大模型
3. 接入地图类 MCP：高德地图官方 MCP Server、百度地图 MCP、Mapbox MCP，用于地理编码、路线规划、POI 搜索与开放时间/票价信息获取
4. 接入天气类 MCP：Weather（AccuWeather）+ KnowAir Weather（彩云天气），为每天和关键时段提供天气与空气质量约束
5. 整合 RAG + 搜索/抓取 MCP：ZZhipu Web Search、Serper 或 Search1API + Browser/Scrapeless，增强行程描述、玩法与注意事项的信息来源
6. 基于 LangGraph 搭建多 Agent 流程：按 Planner → Weather/Constraint Checker → Budget Optimizer → Map/RAG Agent 的顺序编排调用，输出满足约束的行程方案
7. 前后端联调与回归测试：在现有多轮对话界面中串起工具调用链路，重点验证坐标准确性、半小时粒度行程渲染、以及交互过程中的异常与边界情况

4. 基于 Multi-agent/LangGraph 的工作流：划分 Planner、Weather/Constraint Checker、Budget Optimizer、RAG 检索等 Agent，协同完成行程生成、校验与多轮对话中的增量优化

### 延迟优化

1. 先从 4 次 → 2 次
   - 第 1 次：合并“实体抽取 + 意图识别”（可保留可选的摘要更新标记）
   - 第 2 次：行程生成/修改（半小时粒度 + 坐标/城市/街道）
2. 会话摘要改成按需 + 异步
   - 当消息数超过阈值时，后台调一次大模型生成/更新摘要
   - 不再把摘要生成塞在用户同步请求链路里
3. 后续再视情况引入本地小模型
   - 当你接入了 Ollama/本地模型之后，可以把第 1 次调用迁到本地小模型，只保留行程生成用云端/大模型

#### 1.收敛成「2 次大模型调用」
1. 第一次调用：实体抽取 + 意图识别（合并）
- 将原来的 实体抽取 (1) + 意图识别 (3) 合并到一次调用中：
  - 输入：
    - 最近 N 条对话（含用户最新消息）
    - 当前行程简要（如果有）
  - 输出 JSON：
    - entities ：目的地、日期、预算、人数、偏好
    - intent ：none/plan_new/modify_trip/add_attraction/delete_attraction/reorder_trip
    - edit_target ：涉及的天数/景点 id/时段等
  - 优点：
    - 这两个任务高度相关，同一份上下文即可完成
    - 逻辑简单：你只需要一个工具 analyze_user_message 
2. 第二次调用：行程生成/修改（整合一切约束）
- 将原来的 行程生成/修改 (4) 保持单独一步：
  - 在调用前，你已经有：
    - entities （第 1 次输出）
    - intent
    - 现有行程结构（如果存在）
    - 由天气/地图/RAG 工具得到的“硬约束/软约束”（可按需调用 MCP）
    - 已有的长期摘要（不需要每次重新生成）
  - 这一步的大模型只负责：
    - 按半小时粒度输出新的 Itinerary JSON
    - 保证坐标/城市/街道信息存在（你在 v0.0.3 里要求的）

#### 2.收敛成【2次大模型调用】 => 【小模型 + 规则】 + 【1次大模型调用】

1. 小模型：实体抽取、意图识别、会话摘要
2. 大模型：行程生成/修改
