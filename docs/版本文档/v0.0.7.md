# v0.0.7 版本发布规划

## 一、版本定位

v0.0.7 定位为 **“产品打磨与生产环境就绪”** 版本。
本版本的核心侧重于产品完整性的最终校验（横向对比）、用户体验的精细化提升、底层用户资产（Token）的管理与监控，以及最终生产环境的平稳落地。致力于让产品不仅“好用”，还能实现“可管、可控、可观测”，为后续的用户规模增长打下坚实的基础。

## 二、版本目标

> 注：下面`1. 竞品对标与功能查漏补缺 (Feature Completeness)`和`2. 用户体验与 UI 优化 (UI/UX Optimization)`依赖手工自测，这里不需要进行任务规划

### 1. 竞品对标与功能查漏补缺 (Feature Completeness)
* **核心链路梳理**：横向对比主流竞品（明确 2-3 个对标产品），梳理核心用户路径，输出功能差异矩阵。
* **遗漏功能补齐**：针对竞品具备且属于我们产品核心价值闭环内的缺失功能，进行紧急评估和补充开发。
* **边缘场景覆盖**：检查边界条件和异常场景的处理逻辑（如断网、无权限、数据为空时的占位图等），确保功能逻辑的严密性。

### 2. 用户体验与 UI 优化 (UI/UX Optimization)
* **视觉一致性校准**：统一全局的色彩规范、字体排版、组件圆角与间距，确保页面风格的高度统一。
* **交互细节打磨**：
    * 完善各类操作的反馈机制（如按钮点击 Loading 态、成功/失败的 Toast 提示、平滑的过渡动画）。
    * 优化复杂表单或数据录入的校验逻辑，提供更友好的错误引导。
* **响应式与适配性**：针对目标用户常用的设备分辨率进行 UI 适配复测，消除排版错乱、文字截断等视觉 Bug。

### 3. 用户管理系统建设 (User Management System)
* **基础账号体系闭环**：完善用户的注册、登录、密码找回/重置等基础功能（或第三方 OAuth 接入），确保账号安全性。
* **后台管理看板 (Admin Panel)**：
    * **用户列表与状态**：支持后台查看注册用户列表、注册时间、基础信息，并提供账号封禁/解封等基础管理操作。
    * **额度与权限控制**：支持在后台为不同用户配置基础的 Token 额度上限，或设置特定功能的访问权限（为后续商业化或分级运营做准备）。

### 4. 线上监控与可观测性建设 (Monitoring & Observability)
* **用户运行情况监控 (User Activity & Operations)**：
    * 核心埋点与请求时间线：记录用户登录、核心功能调用等关键行为，便于排查用户侧反馈的客诉问题。
    * 接口频率限制 (Rate Limiting)：防止恶意刷量或高频并发导致系统崩溃。
* **Token 消耗与成本监控 (Token & Cost Monitoring)**：
    * **颗粒度统计**：建立基于“全局”和“单用户”双维度的大模型 API 请求 Token 消耗统计表。
    * **预警与熔断机制**：设置平台总 Token 余额预警（如低于 20% 通知管理员），以及单用户额度耗尽时的熔断阻断与前端友好提示。
* **系统运行状态监控 (System Health)**：
    * 核心服务健康检查 (Health Check)、基础指标监控（CPU/内存），以及前端/后端的全局异常日志捕获与实时告警。

### 5. 线上环境部署与发布 (Deployment & Release)
* **部署流程规范化**：完成测试环境与生产环境的隔离，梳理并固化从代码合并到上线的标准操作流程（SOP）。
* **自动化构建 (CI/CD)**：配置流水线，实现代码打包、镜像构建与容器部署的自动化，减少人工干预与出错率。
* **高可用与安全预案**：
    * 确认数据库（尤其是业务数据与 Token 消耗数据）的定期备份策略已生效。
    * 制定并演练“一键回滚”方案，确保在线上出现重大阻碍性 Bug 时，能快速恢复稳定。

### A2. 数据结构设计

#### MySQL 表：`users`

```sql
CREATE TABLE IF NOT EXISTS users (
    id            INT AUTO_INCREMENT PRIMARY KEY,
    email         VARCHAR(255) NOT NULL UNIQUE,
    password_hash VARCHAR(255) NOT NULL,
    nickname      VARCHAR(100) DEFAULT '',
    role          ENUM('user', 'admin') DEFAULT 'user',
    status        ENUM('active', 'banned') DEFAULT 'active',
    token_quota   BIGINT DEFAULT 1000000,         -- 默认 100 万 token 额度
    token_used    BIGINT DEFAULT 0,               -- 已消耗 token
    created_at    DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at    DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_email (email),
    INDEX idx_status (status)
);
```

#### MySQL 表：`password_reset_tokens`

```sql
CREATE TABLE IF NOT EXISTS password_reset_tokens (
    id         INT AUTO_INCREMENT PRIMARY KEY,
    user_id    INT NOT NULL,
    token      VARCHAR(255) NOT NULL UNIQUE,
    expires_at DATETIME NOT NULL,
    used       TINYINT DEFAULT 0,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);
```

#### Redis 键：

- `auth:blocklist:{jti}` — JWT 黑名单（登出/强制失效），TTL = token 剩余有效期
- `user:quota:{user_id}` — 缓存用户额度信息，TTL = 5 min

### B2. 数据结构设计

#### MySQL 表：`token_usage_log`

```sql
CREATE TABLE IF NOT EXISTS token_usage_log (
    id               INT AUTO_INCREMENT PRIMARY KEY,
    user_id          INT NOT NULL,
    session_id       VARCHAR(255) DEFAULT '',
    request_path     VARCHAR(255) NOT NULL,          -- 调用接口路径
    model_name       VARCHAR(100) NOT NULL,           -- 使用的模型
    prompt_tokens    INT DEFAULT 0,
    completion_tokens INT DEFAULT 0,
    total_tokens     INT DEFAULT 0,
    estimated_cost   DECIMAL(10, 6) DEFAULT 0,        -- 估算费用 (USD)
    stage            VARCHAR(50) DEFAULT '',           -- analysis / generation / rag
    created_at       DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_user_id (user_id),
    INDEX idx_created_at (created_at),
    INDEX idx_user_time (user_id, created_at)
);
```

#### MySQL 表：`audit_log`

```sql
CREATE TABLE IF NOT EXISTS audit_log (
    id          INT AUTO_INCREMENT PRIMARY KEY,
    user_id     INT DEFAULT NULL,
    action      VARCHAR(100) NOT NULL,               -- login / register / flow_stream / trip_update / admin_ban 等
    ip_address  VARCHAR(45) DEFAULT '',
    user_agent  VARCHAR(500) DEFAULT '',
    detail      JSON DEFAULT NULL,                    -- 可选扩展字段
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_user_action (user_id, action),
    INDEX idx_created_at (created_at)
);
```

#### Redis 键：

- `ratelimit:{user_id}:{endpoint}:{window}` — 滑动窗口计数器，TTL = window
- `token:global:used` — 全局 Token 消耗累计
- `alert:quota:{user_id}` — 用户额度预警标记，避免重复告警

### 1.1 任务规划（前端 / 后端 / API / 数据结构 / 验收用例）

  - 新增 `src/models/user.py`，统一用户公开信息与重置 token 数据结构。
  - 在 `src/api/app.py` 内新增认证/用户接口，并把会话、聊天、主流程、知识库、行程编辑接口统一切到 JWT 鉴权。
- 本阶段前端聚焦：
  - 新增 `web/src/api/authApi.js`、`web/src/hooks/useAuth.js`、`web/src/components/LoginPage.jsx`。
  - `web/src/api/httpClient.js` 统一注入 `Authorization: Bearer <token>`，401 直接清登录态并回到登录页。
  - `web/src/App.jsx` 改为“未登录显示登录页，登录后进入业务主界面”的单入口结构。
- 本阶段暂不实现：
  - OAuth 真接入
  - 密码找回邮件发送
  - 额度熔断 / Rate Limiting / 请求时间线
- 当前验收目标收敛为：
  - 注册成功后自动获得 token 并进入主页面
  - 登录后所有业务请求自动带 JWT
  - 未登录或 token 失效时，现有业务接口统一拒绝访问
  - 原有会话 / 主流程 / 行程编辑链路全部由当前登录用户驱动

### 1.2 当前实际开发逻辑（截至当前代码）

- 用户数据存储：
  - 当前未沿用旧会话存储表去塞用户字段，而是新增独立 `auth.db` SQLite 库。
  - `users` 表包含 `email/password_hash/nickname/role/status/token_quota/token_used/token_version/created_at/updated_at`。
  - `password_reset_tokens`、`auth_blocklist`、`token_usage_log`、`audit_log`、`rate_limit_log` 已统一建表。
- JWT 认证逻辑：
  - `src/auth/jwt_handler.py` 采用 HS256 生成/校验 token，payload 包含 `sub/email/role/token_version/iat/nbf/exp/jti`。
  - `src/auth/password.py` 使用 `bcrypt` 做密码哈希和校验。
  - `src/auth/middleware.py` 提供 `get_current_user/get_optional_user/require_admin`，统一从 `Authorization` 解析登录用户。
  - 后端在鉴权时会校验用户状态和 `token_version`，因此修改密码后旧 token 会直接失效。
- 管理员与用户管理逻辑：
  - 当前采用“首个注册用户自动成为 admin，后续注册用户默认 user”的策略。
  - 已新增管理员接口：
    - `GET /api/admin/users`
    - `PUT /api/admin/users/{user_id}/status`
    - `PUT /api/admin/users/{user_id}/quota`
    - `GET /api/admin/dashboard`
    - `GET /api/admin/users/{user_id}/token-usage`
    - `GET /api/admin/audit-logs`
  - 管理员可以分页查用户、按邮箱/昵称搜索、封禁/解封、调整额度，并查看 token 使用日志与请求时间线。
  - Dashboard 当前展示总用户数、活跃数、封禁数、管理员数、总配额、总已用、剩余额度。
- 后端接口改造：
  - 已新增：
    - `POST /api/auth/register`
    - `POST /api/auth/login`
    - `POST /api/auth/refresh`
    - `POST /api/auth/forgot-password`
    - `POST /api/auth/reset-password`
    - `GET /api/user/profile`
    - `PUT /api/user/profile`
    - `PUT /api/user/password`
  - 已切换到 JWT 鉴权：
    - `/api/sessions/*`
    - `/api/chat/send`
    - `/api/flow/*`
    - `/api/map/*`
    - `/api/trip/*`
    - `/api/knowledge/*`
  - `GET /api/health` 保留可匿名访问，但会额外返回当前是否已携带有效登录态。
  - 会话接口已加入归属校验，不能跨用户读取、删除、续用别人的 `session_id`。
- 限流与安全控制：
  - 认证接口（注册 / 登录 / 找回 / 重置）当前按 IP 做窗口限流。
  - 已登录业务接口当前按 `user_id` 做窗口限流，管理员走更高阈值。
  - 限流命中后会返回 429，同时写入 `audit_log`，便于排查恶意请求或用户误触发。
- Token 消耗自动累计：
  - `src/llm/llm_manager.py` 已新增 usage observer，能够在真实 LLM 调用完成后把 `prompt_tokens/completion_tokens/total_tokens/model_name/stage` 回传给 API 层。
  - 聊天、主流程中的意图识别、工具路由、FunctionCall、流式生成、非流式生成，都会通过 observer 自动落到 `token_usage_log`。
  - `knowledge/search` 与 `knowledge/answer_from_evidence` 的回答生成链路当前通过统一 token 估算口径补记到 `token_usage_log`，并同步累计到 `users.token_used`。
  - 当前 token 统计仍属于“统一估算口径”，不是底层模型服务商返回的精确 billing token，但已经能形成单用户累计消耗闭环。
- 请求时间线 / 审计时间线：
  - 注册、登录、找回密码、重置密码、额度阻断、限流命中、主流程启动/完成、聊天发送、管理员改状态、管理员改额度等关键动作都会写入 `audit_log`。
  - `/api/sessions/*`、`/api/trip/*`、知识库管理相关接口（知识库列表/创建/删除/上传/链接预处理/链接导入/来源列表/来源删除/来源更新）也已经统一写入审计，管理后台可以看到更完整的用户操作轨迹。
  - 请求时间线字段已扩展为 `user_id/user_email/action/session_id/message_id/request_path/status/detail_json/ip_address/created_at`，足够支撑后续问题追溯与会话时间线查询。
- 额度门禁：
  - 后端已在核心高成本接口增加 `_assert_within_quota`：
    - `/api/chat/send`
    - `/api/flow/stream`
    - `/api/trip/update`
    - `/api/trip/replan_day`
    - `/api/knowledge/search`
    - `/api/knowledge/answer_from_evidence`
  - 当用户 `token_used >= token_quota` 时，接口直接返回 `429 Token 额度已用完，请联系管理员`，并同步写入请求时间线。
- 前端登录流：
  - `web/src/hooks/useAuth.js` 在启动时检查本地 token，有 token 就拉取 `/api/user/profile` 恢复登录态。
  - `web/src/components/LoginPage.jsx` 提供登录 / 注册双模式表单，注册成功后直接进入系统。
  - `web/src/App.jsx` 不再依赖硬编码用户，页面根节点先判断 `isAuthenticated`，未登录只渲染登录页。
  - 顶部 Header 已接入当前用户信息和“退出登录”动作。
  - 前端通过 `authUser.role` 判断是否展示“管理”Tab。
- 前端请求层改造：
  - `web/src/api/httpClient.js` 已统一封装 token 读写、请求头注入和 401 事件广播。
  - 请求层已补充 429/403 友好错误文案：额度耗尽会提示联系管理员，限流命中会提示稍后重试，封禁账号会提示联系管理员。
  - `web/src/api/flowApi.js` 的 SSE 请求已补齐 Bearer Token。
  - `web/src/api/sessionApi.js` 已移除 `user_id` 查询参数写法，直接走当前登录用户。
  - `web/src/hooks/useSessions.js`、`web/src/hooks/useTrip.js` 已移除 `DEFAULT_USER_ID`，只保留 `device_id + session_id`。
  - `web/src/components/AdminPage.jsx` 已支持查看概览统计、搜索用户、封禁/解封、在线编辑并保存额度。

- 当前未完成项：
  - 真正的 SMTP 发信与 OAuth 登录还只是预留接口，不是生产完成态。
  - `forgot-password` 目前是开发态返回 reset token，不走邮件通道。

### 1.3 自测流程

1. 后端启动后，先访问 `GET /api/health`，确认返回 `status=ok`。
2. 前端打开 `http://localhost:5173`，应先进入登录页，而不是直接进入主工作台。
3. 在登录页注册新账号：
   - 输入有效邮箱
   - 输入不少于 8 位的密码
   - 注册成功后应自动进入主页面
4. 注册后刷新浏览器：
   - 应继续保持登录态
   - 会话列表和知识库页面可正常加载
5. 在主页面执行一次核心链路：
   - 新建会话
   - 发送聊天消息
   - 触发行程生成
   - 进入旅行灵感页做一次知识库请求
   - 以上请求都不再需要传 `DEFAULT_USER_ID`
6. 点击右上角“退出登录”：
   - 本地 token 清空
   - 页面应立即回到登录页
7. 手动清空或伪造 token 后再次刷新：
   - 前端应回到登录页
   - 后端业务接口应返回 401/403，而不是继续放行
8. 修改密码后，用旧 token 重新请求接口：
   - 旧 token 应失效
   - 需要重新登录获取新 token
9. 使用首个注册账号登录：
   - 应看到“管理”Tab
   - 进入后应能加载 Dashboard 和用户列表
10. 使用第二个普通账号登录：
   - 不应看到“管理”Tab
   - 直接访问 Admin 接口应返回 403
11. 使用管理员封禁普通用户：
   - 普通用户再次登录应失败，返回“账号已被禁用”
12. 使用管理员把普通用户额度设为 0：
   - 该用户调用主流程 / 对话 / 知识检索时应返回 429
13. 管理员恢复用户状态并提高额度后：
   - 该用户应重新恢复业务访问能力
14. 连续高频访问登录接口或业务接口：
   - 应命中 429 限流
   - 后端 `audit_log` 中应能查到 `rate_limit_blocked`
15. 触发聊天 / 主流程 / 知识回答后：
   - `token_usage_log` 应出现对应记录
   - `users.token_used` 应自动累加
16. 管理员访问 token usage / audit logs 接口：
   - 应能看到单用户 token 消耗记录与关键审计动作
17. 使用普通用户完整执行一次“会话创建 -> 聊天 -> 行程编辑/局部重排 -> 知识库操作”链路后：
   - Admin 页“请求时间线”中应能按 `user_id` 或 `session_id` 筛到这条链路的连续请求记录
   - 涉及主流程流式请求时，日志中还应带出对应 `message_id`


## 模块 B：线上监控与可观测性建设 (Monitoring & Observability)

### 2.1 当前实际开发逻辑（截至当前代码）

- 监控数据存储：
  - 当前监控相关数据统一先落在 `auth.db`，包括 `token_usage_log`、`audit_log`、`rate_limit_log`。
  - 主流程执行指标仍然保留在原有 `flow_metrics.db`，两套数据暂时分库存放。
- Token 消耗追踪：
  - `LlmManager` 通过 usage observer 将真实 LLM 调用摘要上报给 API 层。
  - API 层收到回调后会同时写 `token_usage_log` 并累计 `users.token_used`。
  - `knowledge/search` 与 `knowledge/answer_from_evidence` 的回答生成也已补做 token 估算落库。
- 请求时间线 / 审计时间线：
  - 当前已覆盖认证行为、主流程启动/完成、聊天发送、限流命中、额度阻断、管理员操作，以及 `sessions/trip/knowledge` 相关管理动作。
  - 请求时间线已经补充 `session_id/message_id`，可以支持按用户、按会话、按消息做请求时间线查询。
  - 请求时间线已经可以通过管理员接口查询，并已接到前端 Admin 页的“请求时间线”视图做筛选展示。
- Rate Limiting：
  - 当前实现采用 SQLite 时间窗口方案：
    - 匿名认证接口按 IP 限流
    - 已登录业务接口按 `user_id` 限流
    - 管理员走更高阈值
  - 这是单机部署下的基础版实现，后续若进入多实例部署，需要迁移到 Redis。
- 前端监控可视化：
  - Admin 页当前已经可以直接查看 Dashboard、请求时间线列表、单用户 token 使用日志抽屉，满足基础运营排查场景。
  - 前端请求层已经把额度命中、限流命中、账号封禁转换成更友好的提示文案，减少普通用户看到原始后端报错。
- 当前未完成项：
  - 尚未接入平台总额预警、单用户额度低于阈值告警。
  - 尚未接入前端异常上报和系统资源监控。

### 2.2 自测流程

1. 启动后端与前端后，先使用管理员账号登录，进入“管理”Tab，确认能看到概览卡片、用户管理、请求时间线三个基础区域。
2. 在普通用户侧依次执行注册、登录、聊天发送、主流程生成、知识检索各一次：
   - Admin 页“请求时间线”中应出现 `auth_register`、`auth_login`、`chat_send`、`flow_stream_started`、`flow_stream_completed` 等记录。
3. 在普通用户侧继续执行一次 `session_start -> session_history/session_trip -> trip_update 或 trip_replan_day -> knowledge_*` 操作链：
   - Admin 页“请求时间线”应能看到对应的会话/行程/知识库请求记录。
4. 在 Admin 页“请求时间线”中切换动作筛选，或输入 `user_id/session_id/message_id/request_path`：
   - 列表应只显示匹配条件的请求记录。
   - 其中主流程相关记录应能看到 `message_id`，会话相关记录应能看到 `session_id`。
5. 在普通用户侧触发一次聊天或主流程后，回到 Admin 页用户列表，点击某个用户的“Token 日志”：
   - 右侧抽屉应打开，并展示该用户最近的 `model_name/stage/request_path/prompt_tokens/completion_tokens/total_tokens`。
6. 对同一个普通用户多执行几次聊天、主流程、知识回答：
   - “Token 日志”抽屉中的记录条数应增加。
   - 用户列表中的 `token_used / token_quota` 展示值应同步增长。
7. 将某个普通用户额度调整为较小值，随后继续发起聊天或主流程：
   - 前端应提示“当前账号的 AI 调用额度已用完，请联系管理员调整额度。”
   - Admin 页请求时间线中应出现 `quota_blocked`。
8. 连续高频点击登录或连续快速发送业务请求，触发限流：
   - 前端应提示“你的操作有点频繁了，请稍等片刻再试。”
   - Admin 页请求时间线中应出现 `rate_limit_blocked`。
9. 将某个用户封禁后再尝试登录：
   - 前端应提示“当前账号已被禁用，请联系管理员。”
   - 请求时间线中应能看到对应失败记录。
10. 刷新 Admin 页：
   - Dashboard、用户列表、请求时间线筛选结果、Token 日志查看能力应继续可用，不需要重新手动拼接任何调试参数。
11. 说明：
   - 当前 `token_usage_log` 使用的是统一估算口径，适合运营排查和额度控制；
   - 若后续需要做财务级成本对账，还需要补接模型服务商返回的精确 usage/billing 字段。
