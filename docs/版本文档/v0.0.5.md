# v0.0.5

## 一、文档目标

1. 将当前并列链路统一为“单主流程”，解决主流程、RAG、Agent 入口并行导致的决策复杂问题。
2. 明确 Agent 定位：保留能力，但改为按条件升级的高级模式，默认不启用。
3. 明确 RAG 与 FunctionCall 职责边界，避免重复检索与工具重复调用。
4. 保留流式输出能力，不做整体移除；统一流式事件协议，降低前后端维护成本。
5. 结合竞品补齐未完成能力，并构建可差异化的“极速模式/深度模式”产品策略。

## 二、范围定义

### 2.1 本版本纳入范围

1. 主流程编排统一：在同一请求链路中完成意图识别、上下文组装、工具调用、RAG 检索、结果生成。
2. Agent 模式改造：从独立并列链路改为“主流程内可升级模块”。
3. RAG 链路收敛：RAG 不再作为独立入口，改为主流程中的可选增强步骤。
4. FunctionCall 统一：作为工具调用协议层，统一工具选择、参数生成与结果结构。
5. 流式协议统一：普通模式与 Agent 模式使用同一事件结构，前端按统一状态机渲染。

### 2.2 本版本不纳入范围

1. 不重写底层模型管理框架，不替换现有 LLM 管理组件。
2. 不进行全量前端重构，仅做状态与协议统一所需改造。
3. 不新增复杂商业化模块，仅预留后续商业计划书相关能力接口。

## 三、功能需求

### 3.1 现状问题（基于当前项目结构）

1. 当前存在主流程、RAG、Agent 并列能力入口，路由决策复杂，链路心智负担高。
2. Agent 状态与主流程状态分离，前端展示与恢复逻辑成本高。
3. 工具调用与 RAG 检索边界不清晰，存在重复检索、上下文冗余风险。
4. 普通请求与复杂请求缺乏统一分层策略，导致时延与稳定性波动。

### 3.2 目标架构

1. 建立“单主流程 + 可升级 Agent”统一架构。
2. 主流程固定阶段：
   - 意图识别（生成/修改/问答/复杂任务）
   - 上下文组装（短期会话、摘要、核心实体）
   - 能力路由（工具、RAG、Agent 升级判定）
   - 结果生成（结构化行程或对话结果）
3. 对外保持统一接口，不新增并列业务入口。
4. 流式输出统一协议：`start/delta/end + step`，兼容普通链路与 Agent 链路。

### 3.3 Agent 是否需要

结论：需要，但默认不启用。

1. 保留原因：多步骤依赖、失败重试、人工干预、checkpoint 恢复等复杂任务仍需要 Agent。
2. 默认不启用原因：常规行程生成与修改场景，Agent 会带来额外时延与状态复杂度。
3. 触发策略（满足任一条件可升级 Agent）：
   - 明确多步骤目标（3 步及以上）；
   - 跨城市/跨天强约束联动重排；
   - 工具调用失败需要重试或策略切换；
   - 用户主动开启“深度规划模式”。

### 3.4 RAG 与 FunctionCall 的职责切分

1. FunctionCall 职责：决定调用哪个工具、生成参数、返回标准化工具结果。
2. RAG 职责：在知识不足时提供证据增强，包括公网检索与私有知识库检索。
3. 推荐执行顺序：
   - 先 FunctionCall（天气/POI/地理编码等结构化信息）；
   - 后 RAG（攻略类、知识型、文档型信息）；
   - 最终统一注入上下文生成结果。
4. 约束规则：单次请求内避免同类信息重复检索，控制时延与 token 消耗。

### 3.5 产品能力补齐与差异化

1. 补齐竞品常见能力：统一模式开关、复杂任务可解释触发、失败回退可视化。
2. 差异化能力：
   - 极速模式：禁用 Agent 与深度检索，优先低时延；
   - 深度模式：允许升级 Agent，优先复杂约束满足与可恢复执行。

## 四、非功能需求

1. 性能目标：常规请求平均时延较当前下降 20% 以上。
2. 成本目标：常规请求平均 token 消耗下降 15% 以上。
3. 稳定性目标：主流程成功率不低于当前版本，复杂任务失败可恢复。
4. 可观测性目标：统一记录 `tool_count`、`rag_hit`、`agent_escalated`、`latency` 等关键指标。
5. 可维护性目标：前后端统一状态模型与事件协议，减少双链路维护。

## 五、验收标准

1. 功能验收：
   - 90% 常规请求在不进入 Agent 的情况下正确完成；
   - Agent 仅在命中触发条件时启用，并可返回触发原因；
   - RAG 与工具调用无重复主动作，链路可解释。
2. 性能验收：
   - 常规生成链路时延达成优化目标；
   - token 消耗达成优化目标。
3. 体验验收：
   - 前端仅感知统一主流程状态，不需要区分普通链路与 Agent 链路；
   - 流式响应在两种模式下事件结构一致。
4. 稳定性验收：
   - 复杂任务进入 Agent 后支持暂停、恢复、重试；
   - 异常场景存在明确降级路径并可追踪。

## 六、优先级与实施顺序

### P0（必须）

1. 主流程编排统一（工具/RAG/Agent 路由收敛到单链路）。
2. Agent 改为条件升级模式，默认关闭。
3. RAG 改为主流程子步骤，取消并列心智入口。

### P1（应做）

1. 统一流式事件协议与前端状态消费逻辑。
2. 建立关键指标监控与链路日志追踪。
3. 建立重复检索控制与证据预算约束。

### P2（可选）

1. 上线“极速模式/深度模式”切换策略。
2. 增加复杂任务可解释面板（触发原因、执行阶段、降级路径）。
