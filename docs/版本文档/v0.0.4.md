# v0.0.4

目标：在不破坏现有“行程生成 + Agent 编排 + 联网 RAG”的前提下，引入可复用的第三方能力，补齐“可持续知识库 + 可配置编排 + 可扩展 UI”的工程化短板，让产品具备更强的可扩展性与交付效率。

## 背景与现状（v0.0.3）
- 已有 RAG：偏“联网检索 + 临时向量库”的链路，主要服务于单次查询的证据补充，执行前会清空向量库上下文，不具备持久化知识库能力
- 已有编排：基于 LangGraph 的顺序编排（Planner → Checker → Optimizer → Map/RAG），具备事件/快照与 UI 调试面板
- 已有 UI：Streamlit 为主，适合快速迭代与调试，但对产品化 UI/权限/多端适配能力有限

## 核心需求
### 1.知识库能力升级（RAGFlow 或等价能力）
目标：把“爬虫数据 + 用户上传文档”统一纳入同一套可持久化的知识库/数据集体系，并能够在行程生成链路中按需检索增强。

范围（功能性）：
- 数据源
  - 网页数据：支持将现有“联网检索抓取结果”或“指定 URL 列表”入库
  - 用户文档：支持上传 PDF/Markdown/Docx/纯文本等常见格式（至少先覆盖：PDF/Markdown/纯文本）
- 知识库/数据集
  - 支持创建/删除知识库（或数据集），并支持为一次对话/一次行程选择 1~N 个数据集参与检索
  - 支持对入库内容做元数据标注：来源、时间、标签（目的地/主题/语言）、所属用户/会话（为多用户做准备）
- 检索与证据
  - 支持相似度检索 TopK 与重排（可选），并返回可追溯引用（source/title/片段）
  - 支持“证据预算”控制（长度/条数），避免上下文溢出
- 与行程生成的集成
  - 生成/修改行程时，可选择性开启“知识库检索增强”，并把证据以结构化方式注入到生成 Prompt

可选实现路径（两条都算达标）：
- Path A：集成 RAGFlow 作为外部知识库服务（通过 API 入库/检索）
- Path B：沿用现有 Chroma，但补齐“持久化 collection + 多数据集 + 文档上传解析 + 统一检索接口”

验收标准（最小可用）：
- 能创建至少 1 个知识库并成功导入：1) 10+ 条网页内容 2) 1 个 PDF（或 1 个 Markdown）
- 同一知识库可在多次会话中复用，重启服务后仍可检索到
- 行程生成在开启知识库后：输出中能体现至少 3 条来自知识库的事实性信息，并能给出来源引用

### 2.可配置的流程编排能力（Dify 或等价能力）
目标：让“工具调用 + 多知识库路由 + 回答生成/行程生成”变成可配置的流程，而不是写死在代码里，提升迭代效率与 A/B 能力。

范围（功能性）：
- 编排方式
  - 支持把当前链路拆为可配置节点：输入解析 → 选择知识库 → 检索 → 生成行程 → 校验/优化 → 输出（含地图/证据）
  - 支持为不同场景提供不同流程模板（例如：城市攻略问答 vs 结构化行程生成）
- 工具与接口
  - 现有工具（天气/地理编码/POI/检索）能够以“标准化接口”暴露给编排层调用
  - 支持把“行程生成服务”对外暴露为 API（便于 Dify 调用或未来 Web 前端调用）

可选实现路径（两条都算达标）：
- Path A：集成 Dify 作为外部编排器（TripNexus 以工具/API 形式对接）
- Path B：继续使用 LangGraph，但补齐“流程配置化”（例如：以配置文件/可视化面板选择节点组合、参数与路由规则）

验收标准（最小可用）：
- 可切换至少 2 条流程模板（问答/行程），且无需改代码即可切换
- 任一流程模板能指定使用不同知识库集合（例如：目的地 A 与目的地 B 两套数据集）

### 3.UI 形态升级（Vite + React/Vue + SSR 与 Streamlit 并存）
目标：在不牺牲现有开发效率的前提下，给产品化 UI 留出空间。

建议的范围收敛（避免一次做太重）：
- v0.0.4 不做“完整双 UI 自由切换 + SSR 完整产品”，而是先把核心能力抽象为后端 API
- Streamlit 保留为“调试与管理员后台”
- Vite 前端作为“用户侧产品 UI”（先 CSR，再考虑 SSR）

验收标准（最小可用）：
- 有稳定的后端 API：行程生成、会话列表、知识库检索/导入（至少覆盖核心链路）
- Vite 前端能完成：输入 → 生成行程 → 展示行程（地图可先用 iframe/图片占位）

## 必要性与可行性评估
### 总体判断
- “知识库持久化 + 文档上传”有必要：这是从“演示型 RAG”走向“可复用产品”的关键能力；且与当前“联网检索临时向量库”属于互补，不是重复建设
- “Dify 编排”不一定必要：当前已具备 LangGraph 编排与工具协议，Dify 的价值主要在“可视化配置/运营效率/多人协作”；若团队规模较小或迭代仍偏研发驱动，可先走“内部配置化”，预留 Dify 对接接口
- “双 UI + SSR”短期不必要：工作量大且会分散主线；先 API 化再前端化，能最大化复用与降低重写成本

### 主要风险
- 引入 RAGFlow/Dify 会带来部署与运维复杂度（服务编排、鉴权、资源占用、版本升级）
- 双 RAG 体系并存会造成维护成本上升（建议通过“统一 KnowledgeBase 接口”屏蔽底层差异）
- 多用户/多数据集的权限与隔离设计如果不提前规划，后续会难以补救（至少要在数据模型里预留 user_id/tenant_id）

## 可落地的开发步骤
### M0：接口抽象与边界确定（必须做）
1. 定义统一 KnowledgeBase 接口（入库/检索/数据集管理/引用结构），先不绑定具体实现
2. 定义对外 API 形态（即使暂时只给 Streamlit 调用）：行程生成、知识库管理、检索
3. 明确数据模型：dataset、document、chunk、embedding、引用格式、权限字段（user_id/session_id）

产出：
- KnowledgeBase 接口与统一的检索返回结构（含引用）
- 最小 API 设计（路由与请求/响应结构）

### M1：先落地“本地持久化知识库”（最快闭环）
1. 基于现有 Chroma 实现多 collection/多数据集的持久化存储（不再每次 clear）
2. 接入 Streamlit 文档上传：解析 → 分块 → 入库 → 展示导入结果
3. 在行程生成链路中增加“选择数据集 + 检索 + 注入证据”的开关与参数
4. 增加最小可观测性：导入耗时、chunk 数量、检索命中条数、证据长度

产出：
- 可复用知识库（重启可用）
- 生成行程可引用知识库证据

### M2：评估并接入 RAGFlow（可选，取决于 M1 的痛点）
触发条件（满足其一再做）：
- 需要更强的文档解析/多格式处理/后台管理 UI
- 需要多租户权限、数据集运营、召回/重排的可视化配置
- 需要把知识库能力拆为独立服务（便于多项目复用）

步骤：
1. 以“适配器模式”实现 RAGFlowKnowledgeBase，复用 M0 的统一接口
2. 完成入库/检索的 API 对接与错误回退（RAGFlow 不可用时回退到本地知识库）
3. 增加数据集同步策略（本地与 RAGFlow 的一致性边界与迁移方式）

### M3：编排配置化（先内部，再 Dify）
1. 先把现有 LangGraph 编排做成“可配置模板”（节点启停、参数、路由规则）
2. 把工具与能力通过统一 API 暴露，形成可被外部编排器调用的“工具服务”
3. 若需要可视化编排与运营，接入 Dify：将 TripNexus 的 API/工具注册为 Dify tools，并在 Dify 中实现两条流程模板

### M4：前端产品化（Vite）
1. 先做 CSR：对接 M0/M1 的 API，实现输入/展示/历史会话
2. SSR 仅在需要 SEO 或首屏性能时再引入，避免过早优化
