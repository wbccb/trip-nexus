# TripNexus 整体流程优化方案

## 1. 当前问题诊断

通过对照 `整体流程.md` 与实际代码，确认当前主链路存在以下冗余和低效问题：

### 问题 1：SearchXNR 被重复调用（核心问题）

当前存在 **三个独立的 SearchXNR 触发点**，在一次请求中最多可叠加执行：

| 触发点 | 位置 | 触发条件 |
|--------|------|----------|
| 主流程前置工具阶段 | `flow.py` → `call_tool_by_llm` → `poi.search` | `knowledge_scope != private_only` 且模型判定需要工具 |
| 普通生成路径内部 | `llm_manager.build_trip_prompt` → `call_tool_by_llm` → `poi.search` | 未升级 Agent 时，`build_trip_prompt` 内部再次执行工具预调用 |
| Agent 任务 t2 | `agent_loop.py` → `t2: poi.search` | 升级 Agent 后，SOP 固定执行 |

**最坏情况**：前置工具命中 `poi.search` → 触发 Agent 升级 → Agent t2 再执行一次 `poi.search` = **同一个查询被 SearchXNR 处理两次**。

### 问题 2：前置工具阶段与 Agent 阶段职责重叠

前置工具阶段做了 `poi.search`，但如果因此触发了 Agent 升级，Agent 的 SOP 会从头执行 `t1(天气) → t2(POI) → t3(地理编码)`，**完全无视前置阶段已获取的结果**。

- 前置工具结果通过 `merged_context_texts` 传入 Agent，但 Agent 的 `SharedContext` 并不读取这些数据
- Agent 的 `t2` 会重新构造查询、重新调 SearchXNR、重新做 RAG Pipeline
- 前置阶段的工作 **被浪费**

### 问题 3：Agent 升级条件过于宽松

`_detect_agent_escalation` 的四个条件中：

```
1. mode == "deep"           → 合理
2. days > 7                 → 合理
3. knowledge_query > 20字   → 过于宽松，几乎所有带知识库的请求都满足
4. needs_tool == True       → 形成循环：前置工具命中 → 触发升级 → Agent 重做工具
```

条件 4 是核心矛盾：**前置工具阶段越成功，越会触发 Agent 重做一遍相同的工作**。

### 问题 4：普通路径 `build_trip_prompt` 内嵌二次工具调用

`stream_trip_generation` → `build_trip_prompt` 内部会再次调用 `call_tool_by_llm`，与主流程前置工具阶段形成重复：

```
flow.py:667        call_tool_by_llm(tool_query)     ← 第 1 次
llm_manager.py:804 call_tool_by_llm(tool_query)     ← 第 2 次（在 build_trip_prompt 内部）
```

即使不升级 Agent，普通路径也会执行两次工具调用。

---

## 2. 优化目标

1. **每次请求中 SearchXNR 最多只调用一次**（除非失败重试）
2. **消除前置工具阶段与 Agent/生成阶段的重复工作**
3. **Agent 升级条件合理化**，避免"做了工具就升级、升级后重做工具"的循环
4. **保持功能完整性**：天气、POI、地理编码、私有知识库、冲突检测等能力不丢失
5. **保持流式体验**：前端 SSE 事件流不中断

---

## 3. 优化方案：统一工具层 + 按需升级

### 3.1 核心思路：将工具调用统一到一个层级

**当前架构**（三层都可能调工具）：
```
前置工具层 ──→ [可能调 poi.search]
    │
    ├─→ 普通生成路径 ──→ build_trip_prompt ──→ [可能再调 poi.search]
    │
    └─→ Agent 路径 ──→ t2 ──→ [固定调 poi.search]
```

**优化后架构**（工具只在一个地方执行）：
```
意图识别
    │
    ├─→ 快速路径（mode=fast 且简单请求）
    │     └─→ 统一工具阶段（天气+POI+地理编码，按需执行）
    │     └─→ 私有知识库补充
    │     └─→ generate_trip_pure（纯生成，不再内嵌工具调用）
    │
    └─→ 深度路径（mode=deep 或复杂请求）
          └─→ Agent SOP（t1-t6，工具在 Agent 内部执行）
          └─→ 私有知识库上下文注入 Agent
```

### 3.2 改造点清单

#### 改造点 A：移除 `build_trip_prompt` 内的工具预调用

**文件**：`src/llm/llm_manager.py` → `build_trip_prompt()`

**当前逻辑**（约 line 804）：
```python
if tool_query:
    tool_call = self.call_tool_by_llm(tool_query, ...)
    if tool_call.get("needs_tool"):
        merged_context.append(f"工具结果：{json.dumps(...)}")
```

**改造**：删除 `build_trip_prompt` 内部的 `call_tool_by_llm` 调用。工具结果应该已经通过 `merged_context_texts` 参数传入，不需要内部再调一次。

**影响范围**：`build_trip_prompt` 变为纯 Prompt 构造函数，不再有副作用。

#### 改造点 B：调整 Agent 升级判定，移除 `needs_tool` 条件

**文件**：`src/api/logic/flow.py` → `_detect_agent_escalation()`

**当前条件**：
```python
if flow_mode == "deep":             reasons.append("mode_deep_requested")
if days and days > 7:               reasons.append("long_duration_trip")
if len(knowledge_query) > 20:       reasons.append("complex_knowledge_query")
if tool_result.get("needs_tool"):   reasons.append("tool_usage_required")  # ← 移除
```

**改造为**：
```python
if flow_mode == "deep":             reasons.append("mode_deep_requested")
if days and days > 7:               reasons.append("long_duration_trip")
if len(knowledge_query) > 50:       reasons.append("complex_knowledge_query")  # 提高阈值
# 移除 needs_tool 条件，避免"工具成功→升级→重做"循环
```

**理由**：
- `needs_tool` 触发升级会导致前置工具结果被浪费
- `knowledge_query > 20` 阈值太低（中文 10 个字就超过），提高到 50 更合理
- `mode=deep` 和 `days > 7` 已经足够覆盖真正需要深度规划的场景

#### 改造点 C：前置工具阶段的结果在 Agent 路径中复用

**文件**：`src/api/logic/flow.py` → `_run_flow_stream()` 中启动 Agent 的部分

**当前问题**：前置工具的结果以文本形式在 `merged_context_texts` 中，但 Agent 的 `SharedContext` 不读取它。

**改造方案**：当升级到 Agent 时，将前置工具已获取的结果注入 Agent 的 `SharedContext`，让 Agent 跳过已完成的任务。

```python
# 在调用 run_agent_loop_sync 前，构造预填充数据
prefilled = {}
if tool_result and tool_result.get("needs_tool"):
    tool_name = tool_result.get("tool_name")
    if tool_name == "poi.search":
        prefilled["t2"] = {"poi": tool_result.get("result", {})}
    elif tool_name == "weather.get_daily":
        prefilled["t1"] = {"weather": tool_result.get("result", {})}

agent_result = run_agent_loop_sync(
    ...,
    prefilled_context=prefilled  # 新增参数
)
```

**文件**：`src/agent/agent_loop.py`

**改造**：
- `_build_sop_plan()` 或 `_schedule_tasks()` 中检查 `prefilled_context`
- 如果某个任务的输出已经被预填充，直接标记为 `completed`，跳过执行
- 这样即使升级到 Agent，已经做过的 POI 搜索不会重做

#### 改造点 D：统一非 Agent 路径的工具执行流程

**文件**：`src/api/logic/flow.py` → `_run_flow_stream()`

**当前**：
```
前置工具阶段 → call_tool_by_llm (可能命中 poi.search)
    ↓
stream_trip_generation → build_trip_prompt → call_tool_by_llm (又来一次)
```

**改造后**：
```
前置工具阶段 → call_tool_by_llm (执行一次，结果写入 merged_context_texts)
    ↓
stream_trip_generation → build_trip_prompt (纯构造 Prompt，使用已有 context)
    ↓
generate_trip_pure 或 stream_llm_text (纯生成)
```

具体做法：让普通生成路径也使用 `generate_trip_pure`（或使用改造后的不含工具调用的 `build_trip_prompt`），统一生成逻辑。

## 4. 优化后的完整流程图

```
前端表单提交
→ useTrip.handleFlowSubmit 组装 payload
→ flowApi.streamMainFlow 建立 SSE
→ /api/flow/stream 创建 stream_state
→ _run_flow_stream 开始主流程

  ┌─ Step 1: 意图识别
  │  → llm_manager.analyze_user_message
  │  → 输出: generate_trip / modify_trip / general_conversation
  │
  ├─ Step 2: 路由分叉判定（提前到工具执行之前）
  │  → 判断是否进入 Agent 路径
  │  → 条件: mode=deep OR days>7 OR knowledge_query>50
  │
  ├─── 快速路径（不升级 Agent）─────────────────────────┐
  │  ┌─ Step 3a: 统一工具阶段                           │
  │  │  → call_tool_by_llm (一次，结果缓存)              │
  │  │  → 结果写入 merged_context_texts                 │
  │  │                                                  │
  │  ├─ Step 4a: 私有知识库补充                          │
  │  │  → _build_knowledge_context_payload               │
  │  │  → 结果追加到 merged_context_texts                │
  │  │                                                  │
  │  ├─ Step 5a: 上下文预算裁剪                          │
  │  │  → _merge_context_with_budget                     │
  │  │                                                  │
  │  ├─ Step 6a: 纯行程生成（不含内嵌工具调用）            │
  │  │  → generate_trip_pure (或改造后的 build_trip_prompt)│
  │  │  → stream_llm_text → 流式返回                    │
  │  └──────────────────────────────────────────────────┘
  │
  ├─── 深度路径（升级 Agent）────────────────────────────┐
  │  ┌─ Step 3b: 私有知识库补充（先做，注入 Agent 上下文）  │
  │  │  → _build_knowledge_context_payload               │
  │  │                                                  │
  │  ├─ Step 4b: Agent SOP 执行                         │
  │  │  → t1: weather.get_daily                         │
  │  │  → t2: poi.search (SearchXNR 仅在此触发)          │
  │  │  → t3: geo.geocode                               │
  │  │  → t4: generate_trip_pure                        │
  │  │  → t5: map_render                                │
  │  │  → t6: trip_summarize                            │
  │  └──────────────────────────────────────────────────┘
  │
  ├─ Step 7: 后处理（两条路径汇合）
  │  → 约束满足状态计算
  │  → 冲突检测与替代方案
  │  → 会话落库
  │
  └─ Step 8: SSE finalize 返回 trip_data
     → 前端渲染行程 / 地图 / 冲突 / 调试信息
```

## 5. 关键改动对比

| 维度 | 当前实现 | 优化后 |
|------|---------|--------|
| SearchXNR 调用次数 | 最多 2-3 次 | 最多 1 次 |
| 前置工具 → Agent 结果复用 | 不复用，Agent 全部重做 | 预填充 SharedContext，跳过已完成任务 |
| `build_trip_prompt` 内嵌工具调用 | 有，造成重复 | 移除，变为纯 Prompt 构造 |
| Agent 升级条件 | `needs_tool` 导致循环升级 | 移除该条件，只保留合理触发 |
| `knowledge_query` 阈值 | 20 字（过低） | 50 字（更合理） |
| 路由分叉时机 | 工具执行后判断 | 工具执行前判断（深度路径）或工具执行后判断（快速路径） |
| 普通路径生成方式 | `stream_trip_generation`（内嵌工具） | `generate_trip_pure`（纯生成） |

## 6. 改造文件影响范围

| 文件 | 改动内容 | 影响程度 |
|------|---------|---------|
| `src/api/logic/flow.py` | 调整路由分叉时机、移除 `needs_tool` 升级条件、添加 Agent 预填充逻辑 | 高 |

| 私有知识库相关 | 无需改动 | 无 |
| RAG Pipeline / SearchXNR | 无需改动（调用方减少，内部逻辑不变） | 无 |

## 7. 实施步骤建议

### Phase 1：消除普通路径的重复工具调用（风险最低，收益明确）

1. 修改 `build_trip_prompt`，移除内部 `call_tool_by_llm` 调用
2. 确保前置工具阶段的结果通过 `merged_context_texts` 正确传入
3. 验证：普通路径下 SearchXNR 从 2 次降为 1 次

### Phase 2：优化 Agent 升级条件

1. 从 `_detect_agent_escalation` 移除 `needs_tool` 条件
2. 将 `knowledge_query` 阈值从 20 提高到 50
3. 验证：`mode=fast` 的短行程不再被意外升级到 Agent

### Phase 3：Agent 路径复用前置工具结果

1. `flow.py` 中构造 `prefilled_context` 传入 Agent
2. `agent_loop.py` 中支持跳过已预填充的任务
3. 验证：即使升级 Agent，已做过的 POI 搜索不会重复

### Phase 4（可选）：路由分叉前置

1. 将 Agent 判定提前到工具执行之前
2. 深度路径直接进入 Agent，不再经过前置工具阶段
3. 快速路径保留前置工具 + 纯生成
4. 验证：深度路径的整体延迟降低（少了一次前置工具执行）

## 8. 风险与回退

| 风险 | 缓解措施 |
|------|---------|
| 移除 `build_trip_prompt` 内工具调用后，普通路径生成质量下降 | 前置工具阶段已提供等效上下文；可通过 A/B 测试验证质量 |
| 修改升级条件后，部分复杂请求未进入 Agent | 监控 `agent_escalated` 指标；如需要可增加新的合理条件 |
| Agent 预填充逻辑引入新 bug | Agent 内部对预填充数据做格式校验；不符合预期时回退到正常执行 |

**回退策略**：每个 Phase 独立可回退。通过配置开关控制是否启用优化逻辑，上线初期可灰度对比。

---

## 9. 预期收益

- **延迟降低**：消除 1-2 次 SearchXNR 调用，每次 SearchXNR 含网络搜索+网页抓取+向量化，耗时约 3-8 秒
- **成本节约**：减少 LLM 调用次数（`call_tool_by_llm` 内部有模型决策调用）
- **架构清晰**：工具调用只在一个层级发生，排查问题更容易
- **日志可读性提升**：不再看到令人困惑的多次 SearchXNR 日志
