# TripNexus 当前【生成旅游规划】整体流程

## 1. 文档目标

这份文档不是讲“理想设计”，而是按**当前代码真实实现**去拆解：

- 前端从哪里发起“生成旅游规划”
- 后端 `/api/flow/stream` 实际做了哪些步骤
- 私有知识库、公网检索、工具调用、Agent、LLM 生成分别在什么位置介入
- 为什么日志里会看到 **SearchXNR 被调用多次**
- 最终 `trip_data` 是如何流式返回并落库的

为了覆盖目前最复杂、也最接近真实线上主链路的场景，下面统一使用这个示例来说明。

---

## 2. 说明示例

### 2.1 用户在前端填写

- 目的地：成都
- 天数：3
- 预算：3000 元
- 偏好：人文、美食
- 约束：
  - `budget_level=balanced`
  - `intensity=standard`
  - `pace=cultural`
  - `need_nap=true`
- 已选择一个私有知识库：`kb_chengdu_notes`
- `knowledge_scope=private_plus_public`
- `mode=fast`

### 2.2 前端最终发往主流程的大致 payload

```json
{
  "device_id": "xxx",
  "session_id": "当前会话ID",
  "destination": "成都",
  "days": 3,
  "mode": "fast",
  "budget": "3000 元",
  "preference": "人文、美食",
  "context_texts": [],
  "knowledge_base_id": "kb_chengdu_notes",
  "knowledge_query": "目的地:成都 偏好:人文、美食 行程建议",
  "knowledge_scope": "private_plus_public",
  "budget_level": "balanced",
  "intensity": "standard",
  "pace": "cultural",
  "special_constraints": {
    "walking_limit_km": null,
    "need_nap": true,
    "accessibility": false
  }
}
```

这个 payload 的来源不是聊天接口，而是前端的“行程输入弹窗”。

## 3. 一句话先说结论

当前“生成旅游规划”的真实主链路是：

**前端表单提交 → `/api/flow/stream` 建立 SSE → 意图识别 → 工具路由 → 私有知识库补充 → 判断是否升级 Agent → Agent 或直接 LLM 生成 → 冲突检测/约束回填 → 会话落库 → SSE finalize 返回前端**

其中最容易让人误判的点有两个：

1. **主流程里的公网检索不是固定直接跑一遍 RAG**，而是通常通过 `poi.search` 这个工具间接触发。
2. **只要主流程前置工具阶段命中了工具，就很容易升级到 Agent**，而 Agent 计划里又会再执行一次 `poi.search`，这就是日志里会看到 **SearchXNR 多次调用** 的核心原因。

## 4. 端到端完整流程

## 4.1 前端入口：用户点击“生成行程”

前端入口在 `web/src/App.jsx` 的 `handleFlowFormSubmit`：

1. 读取表单值
2. 拼出一条展示在聊天区的“用户消息”
3. 调用 `handleFlowSubmit(values, ...)`
4. 在聊天区先放一个“行程生成中...”的占位消息

这里前端只负责：

- 收集结构化输入
- 展示流式状态
- 接收最终 `trip_data`

真正的编排逻辑都在后端主流程里。

---

## 4.2 前端请求封装：`useTrip.handleFlowSubmit`

`web/src/hooks/useTrip.js` 会把表单值归一化后发出去：

### 关键动作

1. 补齐结构化约束字段
2. 构造默认 `knowledge_query`
3. 把知识库 ID、知识范围、约束一起带上
4. 调用 `streamMainFlow`

这里的一个重要细节：

- `knowledge_scope=private_plus_public` 不只是 UI 上的选项
- 它会直接影响后端是否允许公网补充能力介入

---

## 4.3 SSE 建链：`flowApi.streamMainFlow`

前端通过 `fetch + ReadableStream` 调 `/api/flow/stream`，而不是一次性普通 POST。

它会持续解析后端发回来的 SSE 事件：

- `start`
- `delta`
- `end`

并且维护两个关键状态：

- `message_id`：用于同一条流任务标识
- `sequence`：用于断线续传

也就是说，前端看到的“逐字输出”“流程状态刷新”“最终落地结果”，本质上都来自后端不断推送的事件。

---

## 4.4 后端流式入口：`/api/flow/stream`

路由入口在 `src/api/routes/flow.py`。

它先做四件事：

1. 校验登录态与配额
2. 补齐或校验 `session_id`
3. 创建/复用 `stream_state`
4. 启动异步任务 `_run_flow_stream(...)`

然后把同一个 `stream_state.events` 中新增的事件不断以 SSE 形式吐给前端。

所以路由本身不是“做规划”，而是：

- 启动后台主流程
- 持续转发主流程产生的事件

---

## 4.5 主流程真正开始：`_run_flow_stream`

核心逻辑在 `src/api/logic/flow.py` 的 `_run_flow_stream`。

下面按真实执行顺序展开。

### 第 1 步：初始化用户输入与约束

主流程先把表单字段收敛成 `user_input`：

```text
destination / days / budget / preference
+ budget_level / intensity / pace / special_constraints
```

也就是：前端表单虽然看起来是“自由填写 + 部分选项”，但进入后端后会被规范成一个稳定结构。

### 第 2 步：发送 `intent.start`

主流程先向前端发一个 `step=intent` 的 `start` 事件，表示任务已经进入“识别意图”阶段。

这也是前端状态栏里可以显示“当前流程正在干什么”的基础。

### 第 3 步：意图识别

主流程会构造 `flow_query`：

- 如果请求里有 `message`，优先用 `message`
- 否则退化成：`规划去{destination}的{days}天行程`

然后调用：

- `llm_manager.analyze_user_message(flow_query, context_messages, current_trip)`

这一层会判断当前请求属于：

- `generate_trip`
- `modify_trip`
- `general_conversation`
- 其他调整类意图

对于当前示例，通常会被识别为：

- `generate_trip`

随后主流程向前端发一个 `intent.done` 事件。

---

## 4.6 工具路由阶段：第一次可能触发 SearchXNR

接下来进入 `step=tool`。

主流程会先构造 `tool_query`，内容大概是把这些信息拼成自然语言：

- `flow_query`
- `destination`
- `preference`

然后在满足下面条件时才会尝试工具调用：

- `tool_query` 不为空
- `knowledge_scope != private_only`

也就是说，**只有允许公网补充时，主流程前置工具阶段才会运行**。

### 这一段会做什么

主流程调用：

- `llm_manager.call_tool_by_llm(tool_query, context_messages)`

内部流程是：

1. 先让分析模型判断“需不需要工具”
2. 如果要工具，再决定调用哪个工具
3. 执行工具
4. 把工具结果写回 `merged_context_texts`

### 为什么这里会打到 SearchXNR

如果分析模型判定当前示例最适合调用：

- `poi.search`

那么调用链会变成：

```text
call_tool_by_llm
→ call_tool("poi.search")
→ search_poi(...)
→ AIRetrievalPipeline.run(...)
→ MultiSourceSearcher.search(...)
→ _search_searxng(...)
→ SearchXNR/SearXNG 实例搜索
```

然后会继续走：

```text
SearchXNR 搜索结果
→ 质量过滤
→ 网页抓取
→ 向量化
→ Body Evidence 召回
→ 可选 RAG answer
```

### 日志里通常会看到的关键词

这一段最典型的日志关键词来自 `src/rag/rag_main.py`：

- `【RAG】准备开始SearchXNR搜索url列表`
- `SearchXNR得到: ...`
- `RAG 搜索完成`
- `RAG 质量过滤完成`
- `RAG 内容抓取完成`
- `RAG 向量检索完成`

### 这一阶段的结果怎么被使用

如果工具调用成功，主流程不会直接把搜索结果当最终答案返回，而是会把结果注入上下文：

```text
merged_context_texts.append("工具结果：...")
```

也就是说，这次 SearchXNR 的产物本质上是：

- 给后面的行程生成补充参考事实
- 不直接等于最终 `trip_data`

---

## 4.7 私有知识库补充：这一步不会触发 SearchXNR

接下来主流程调用：

- `_build_knowledge_context_payload(...)`

这一层做的是：

1. 根据 `knowledge_base_id` 找到对应向量集合
2. 生成知识库检索 query
3. 对私有知识库做 `similarity_search(query_text, k=4)`
4. 把命中的文档拼成 `context_texts`
5. 抽取 `source_evidence`

### 这里要特别注意

这一步是：

- **查私有知识库向量集合**

不是：

- 跑公网 SearchXNR

所以当前主流程里“私有知识补充”和“公网 SearchXNR”是两条不同能力线：

- 私有知识：`_build_knowledge_context_payload`
- 公网搜索：通常通过 `poi.search -> AIRetrievalPipeline.run -> SearchXNR`

### 当前示例里，这一步的作用

如果 `kb_chengdu_notes` 里提前导入了小红书攻略、Markdown、PDF、手工整理内容，那么这里会把最相关的 4 条片段压缩成：

- `私有知识库参考（来源:...）：...`

并拼入后续 LLM Prompt 上下文。

---

## 4.8 上下文预算裁剪

主流程不会把所有上下文无限塞给模型，而是做预算控制：

- 最多 12 条
- 单条最多 600 字
- 总计最多 3200 字

超过预算后会截断。

这一步的作用是：

- 避免 Prompt 失控
- 保证工具结果、私有知识、用户输入能同时进入模型

---

## 4.9 路由分叉：是否升级到 Agent

然后进入 `_detect_agent_escalation(...)`。

当前代码里会触发升级的条件是：

1. `mode=deep`
2. 生成行程且天数大于 7
3. `knowledge_query` 很长
4. **前置工具阶段命中了工具**

第 4 条非常关键。

也就是说，对于我们这个示例，只要前面工具阶段真的命中了 `poi.search`，哪怕前端传的是 `mode=fast`，当前实现依然很可能升级到 Agent。

---

## 4.10 Agent 深度规划：第二次可能触发 SearchXNR

如果升级到 Agent，主流程不会直接执行 `stream_trip_generation`，而是进入：

- `run_agent_loop_sync(...)`

Agent 的默认 SOP 计划在 `src/agent/agent_loop.py` 中，大致是：

1. `t1` 查询天气
2. `t2` 查询 POI
3. `t3` 查询目的地地理编码
4. `t4` 生成行程草案
5. `t5` 渲染地图
6. `t6` 生成摘要

### 为什么这里又会出现 SearchXNR

因为 `t2` 固定就是：

- `tool="poi.search"`

而 `poi.search` 内部仍然会走：

- `AIRetrievalPipeline.run(...)`
- `MultiSourceSearcher.search(...)`
- `SearchXNR`

所以如果前面主流程前置工具阶段已经跑过一次 `poi.search`，那么进入 Agent 后，**这里会再跑一次**。

这就是目前“生成旅游规划”里最典型的 **SearchXNR 多次调用来源**。

---

## 4.11 Agent 内部每个任务的真实作用

### t1：天气

- 工具：`weather.get_daily`
- 用途：给行程生成提供天气条件

### t2：POI

- 工具：`poi.search`
- 用途：补充热门景点/候选地点/联网证据
- 特点：最容易触发 RAG 与 SearchXNR

### t3：地理编码

- 工具：`geo.geocode`
- 用途：给地图渲染与地址坐标补全提供基础位置

### t4：生成行程草案

这里调用的是：

- `llm_manager.generate_trip_pure(state.user_input, context_payload)`

注意它是 **pure** 版本，不会再做内置工具预调用。

这一点很关键，因为它说明：

- Agent 路径里，工具阶段和生成阶段被拆开了
- `t4` 只负责基于已有上下文生成 JSON 行程
- 它不会在 `t4` 内部再次触发一轮 `poi.search`

### t5：地图渲染

- 把 `draft_trip` 喂给地图渲染器
- 产出 `map_payload`

### t6：行程摘要

- 从 `draft_trip` 里提取一个简单摘要文本

### Agent 最终产出

Agent finalize 时只收敛三类结果：

- `draft_trip`
- `map_payload`
- `summary`

其中主流程真正继续往后用的是：

- `draft_trip`

---

## 4.12 如果没有升级到 Agent，会走哪条路

如果前置工具阶段没有命中工具，或者没有达到升级条件，那么主流程会走普通生成路径：

```text
llm_manager.stream_trip_generation(user_input, merged_context_texts)
→ build_trip_prompt(...)
→ stream_llm_text(...)
→ build_stream_events_from_stream(...)
→ 拼接 response_text
→ parse_trip_from_response_text(...)
```

### 这一条路径里也可能出现 SearchXNR

因为 `build_trip_prompt(...)` 内部还有一层“工具预调用”：

```text
build_trip_prompt
→ _build_tool_query(...)
→ call_tool_by_llm(...)
```

如果这里命中 `poi.search`，依然会触发 SearchXNR。

所以当前实现里，SearchXNR 可能出现在两个位置：

1. 主流程前置工具阶段
2. 普通生成路径里的 `build_trip_prompt`

但如果已经升级到 Agent，则普通生成路径不会再执行。

---

## 4.13 LLM 最终生成的不是自然语言，而是结构化 JSON

不管是普通路径还是 Agent 路径，最终核心都要生成一个严格 JSON 结构的行程对象。

Prompt 中明确要求输出：

- `destination`
- `days`
- `daily_plan`
- 每个行程项的时间、地点、坐标、交通、评分、标签、来源链接等

这也是为什么前端最终能够：

- 展示列表行程
- 渲染地图
- 做拖拽编辑
- 做局部重排

因为它接收到的不是一段“攻略文案”，而是结构化行程数据。

---

## 4.14 主流程生成完成后的后处理

一旦拿到 `trip_data`，主流程还没结束，还会继续做三件事：

### 1. 约束满足状态计算

调用：

- `_build_constraint_statuses(trip_data, constraints_used)`

作用：

- 判断预算档位、节奏、午休、步行限制等是否满足

### 2. 冲突检测与替代方案

调用：

- `llm_manager.build_conflict_report(trip_data, constraints_used)`

作用：

- 检查跨城跳跃
- 时间冲突
- 体能密度过高
- 午休冲突
- 生成替代方案

如果发现冲突，会先推一个：

- `step=warning`

给前端，让冲突区先亮起来。

### 3. 会话落库

调用：

- `_get_storage().store_trip_data(session_id, trip_data)`

作用：

- 把最终行程写回当前会话
- 后续编辑、重排、回看历史都基于这份数据

---

## 4.15 主流程最终 SSE 返回给前端什么

最后主流程会发送一个 `event=end`、`step=finalize` 的最终事件。

payload 里关键字段有：

- `trip_data`
- `response_text`
- `metrics`
- `constraints_used`
- `constraints_satisfied`
- `conflict_report`
- `source_evidence`
- `knowledge_debug`
- `agent_escalated`
- `escalation_reasons`

前端收到后会：

1. 更新聊天区最终文本
2. 更新中间区域行程详情
3. 更新冲突区
4. 更新知识命中调试区
5. 记录运行时指标

到这里，一个“生成旅游规划”的完整闭环才真正结束。

---

## 5. 为什么当前会看到多次 SearchXNR

## 5.1 最常见场景

以当前示例来说，最常见的两次 SearchXNR 是：

### 第 1 次：主流程前置工具阶段

```text
_run_flow_stream
→ call_tool_by_llm
→ poi.search
→ AIRetrievalPipeline.run
→ SearchXNR
```

### 第 2 次：升级到 Agent 后的 `t2`

```text
run_agent_loop_sync
→ Agent SOP task t2
→ poi.search
→ AIRetrievalPipeline.run
→ SearchXNR
```

---

## 5.2 为什么会重复

本质原因不是 SearchXNR 自己重复，而是**当前架构里有两个不同层级都可能独立做 POI 检索**：

1. 主流程前置工具增强
2. Agent 计划执行中的 POI 任务

它们的职责目前并没有做“结果复用合并”，所以会各自发起一次检索。

---

## 5.3 可能更多次的情况

如果出现下面情况，SearchXNR 次数还会继续增加：

1. Agent 的 `poi.search` 任务失败后重试
2. Reflector 判断结果太差，触发 replan
3. 普通生成路径中 `build_trip_prompt` 再次命中 `poi.search`
4. 用户后续局部重排、修改行程时又触发新的工具调用

所以日志里看到 2 次以上 SearchXNR 并不一定是 bug，也可能是当前实现的正常结果。

---

## 6. 把这条链路压缩成一张“执行顺序图”

```text
前端表单提交
→ useTrip.handleFlowSubmit 组装 payload
→ flowApi.streamMainFlow 建立 SSE
→ /api/flow/stream 创建 stream_state
→ _run_flow_stream 开始主流程
→ intent 分析
→ tool 路由
  → 若命中 poi.search
    → RAG Pipeline
    → SearchXNR 第 1 次
→ 私有知识库 similarity_search
→ 上下文预算裁剪
→ _detect_agent_escalation
  → 若升级 Agent
    → Agent t1 天气
    → Agent t2 poi.search
      → RAG Pipeline
      → SearchXNR 第 2 次
    → Agent t3 geocode
    → Agent t4 generate_trip_pure
    → Agent t5 map_render
    → Agent t6 summary
  → 若不升级 Agent
    → stream_trip_generation
    → parse_trip_from_response_text
→ 约束满足计算
→ conflict_report 计算
→ store_trip_data 落库
→ SSE finalize 返回 trip_data
→ 前端渲染行程 / 地图 / 冲突 / 调试信息
```

## 7. 当前实现最值得注意的几个事实

### 事实 1：主流程里的 `knowledge_scope` 不等于“固定先跑一遍公网 RAG”

当前主流程下：

- 私有知识库检索是 `_build_knowledge_context_payload`
- 公网补充更多是通过工具链 `poi.search` 间接完成

### 事实 2：前置工具一旦命中，很容易直接进入 Agent

因为 `_detect_agent_escalation` 把：

- `tool_result.get("needs_tool")`

直接作为升级条件之一。

### 事实 3：Agent 路径反而更“分层”

Agent 下：

- 工具任务单独做
- 行程生成用 `generate_trip_pure`
- 不会在生成阶段再偷偷内嵌一次工具调用

### 事实 4：普通路径和 Agent 路径的 SearchXNR 触发点不同

- 普通路径：可能在 `build_trip_prompt` 里触发
- Agent 路径：主要在工具任务里触发

### 事实 5：最终对前端真正重要的是 `finalize`

因为只有 `finalize.payload.trip_data` 才是最终持久化版本。

---

## 8. 用当前示例对照日志时，建议重点盯的关键词

如果要验证这条链路，建议按下面顺序看日志：

1. `/api/flow/stream` 是否成功进入
2. 是否出现 `意图识别完成：generate_trip`
3. 是否出现 `工具选择完成` / `工具执行完成`
4. 是否出现 `【RAG】准备开始SearchXNR搜索url列表`
5. 是否出现 `knowledge_context_search`
6. 是否出现 `进入深度规划流程`
7. 是否出现 Agent 的 `t1/t2/t3/t4/t5/t6`
8. 是否出现 `行程 JSON 解析成功` 或最终 `trip_data`
9. 是否出现 `warning`
10. 是否出现 `finalize`

如果你在日志里看到两次 `【RAG】准备开始SearchXNR搜索url列表`，优先按这条思路理解：

- 第一次通常来自主流程前置工具阶段
- 第二次通常来自 Agent 的 `t2=poi.search`

## 9. 最终可验证的输出物

一次成功的“生成旅游规划”最终至少会产出这些结果：

- 前端聊天区有最终回复或生成中的流式文本
- `trip_data` 成功返回
- 行程详情可展示
- 地图可渲染
- `constraints_used / constraints_satisfied` 可见
- `conflict_report` 可见

如果带知识库：

- `source_evidence` 会返回本次真正命中的私有来源

如果走 Agent：

- `agent_escalated=true`
- `escalation_reasons` 非空

## 10. 这份文档对应的核心判断

对当前项目来说，“生成旅游规划”并不是简单的一次 LLM 调用，而是一个**主流程编排器**：

- 先做识别
- 再做工具增强
- 再做私有知识补充
- 再决定是否进入 Agent
- 最后才生成结构化行程

而你现在觉得复杂、尤其是 SearchXNR 会多次触发，这个感觉是对的。  
因为当前实现确实已经形成了：

- **主流程前置工具层**
- **Agent 任务执行层**
- **私有知识向量检索层**
- **最终行程生成层**

这几层叠加后，才构成现在完整的“生成旅游规划”链路。
